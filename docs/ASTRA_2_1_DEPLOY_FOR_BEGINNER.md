# План будущего ручного внедрения через браузер

Сейчас НЕ выполнять. Кандидат требует ревью PR и staging по ASTRA_2_1_MIGRATION.md. Реальных подключений и деплоя в этом задании нет.

1. Открыть PR, проверить diff, аудит и результаты тестов. Сохранить копию текущего Worker 2.0 и проверенный backup D1. Убедиться, что выбран именно нужный аккаунт/Worker и production binding DB → astra-live-v2. Не передавать секреты Codex.
2. Создать отдельную staging D1/Worker. Для тестового сценария использовать отдельного Telegram-бота, никогда не менять webhook работающего бота. Его настройка выполняется владельцем отдельно. Пройти матрицу staging и контрольные SQL. Внешние тесты здесь не выполнены.
3. Только после успешного staging согласовать короткое окно обслуживания. В Dashboard Workers & Pages открыть нужный Worker → Edit code. Сохранить текущую версию. Для паузы использовать целиком `release/ASTRA_2_1_MAINTENANCE.js`, если владелец отдельно разрешил публикацию. Он отвечает webhook 503 и не пишет из Cron. Дождаться завершения старых запросов. Операция влияет на доступность бота — не делать без решения владельца.
4. D1 → выбранная база → Console: выполнить полный файл `migrations/0021_wallet.sql`. Проверить агрегаты полным набором запросов из `scripts/check_integrity.sql` и сравнить с backup. При ошибке остановиться; не удалять таблицы, не отключать ограничения и не возвращать пишущий v2.
5. Workers & Pages → тот же Worker → Edit code: заменить весь JS содержимым `release/ASTRA_2_1_WORKER.js`, а не добавить в конец. Это готовый single-file ES module; сборка/npm не нужны. Проверить, что binding, секреты, URL и Cron сохранены. Только после отдельного разрешения владельца — Deploy. Автоматический CI-деплой не настроен.
6. Во вкладке Deployments сверить активную версию. Открыть публичный `/health`: version ASTRA-2.1.0-candidate, schema_ready и ready true. Он не показывает ID/тексты/значения секретов. Worker root сохранён. Не ориентироваться на Preview.
7. Webhook **не переактивировать**. Путь `/telegram-webhook` и заголовок секрета прежние. Старый `/activate?key=...` в 2.1 отключён (410), API setWebhook вообще отсутствует в кандидате. Если когда-либо понадобится менять webhook, нужен отдельный контролируемый процесс владельца с авторизацией вне URL и `drop_pending_updates:false`; для этого обновления он не нужен. Не вводить admin key в адресную строку.
8. На собственных тестовых профилях владельца проверить /start, знак, бесплатный прогноз с числом дня, карту дня, бонус один раз, баланс, подписку, реферал, Таро −3, повтор кнопки, /stop и рассылку, privacy/delete. Не тестировать реальные платежи: Telegram Stars не реализованы. Для нового платного расклада заново открыть меню «Таро». Старая кнопка того же сообщения не продаёт второй расклад.
9. Контроль ledger: запросы scripts/check_integrity.sql. Дополнительная внутренняя проверка — POST `/internal/integrity` с `Authorization: Bearer <admin key>` из доверенного инструмента владельца. Не помещать ключ в URL/чат/скриншоты/историю shell. Возвращает только число расхождений, не данные пользователей.
10. При расхождении денег или массовых ошибках — maintenance Worker, сохранить данные/логи без персональных текстов, исправление и повтор staging. Нельзя откатывать на оригинальный пишущий v2 поверх новой схемы. Подробнее — раздел отката в миграции.

Cron остаётся прежним: * 6-7 * * *, 09:00–10:59 Москвы, до 8 попыток за invocation. Теоретически 960 за окно, фактически меньше из-за сбоев/лимитов. Нет автоматической новой очереди, повышения тарифов или рассылок. Неопределённые/отклонённые попытки не переотправляются автоматически в тот же день: возможны пропуски. Пользователь может бесплатно получить прогноз кнопкой. Рост аудитории требует отдельной очереди и staging-нагрузки.
