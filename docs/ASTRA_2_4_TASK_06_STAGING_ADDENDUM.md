## Перед любым изменением

1. Получить отдельное разрешение на конкретные staging Worker и D1 **astra-staging-21**; сверить database ID и binding `DB`. Имена не заменяют проверку. Если база не содержит полную 2.3B, остановиться и согласовать иной исходный маршрут.
2. Выполнить разделы backup/отдельной восстановленной копии/защищённого сравнения из `ASTRA_2_4_TASK_05_STAGING_GUIDE.md`. Time Travel bookmark без отдельного восстановления не закрывает проверку. В копии сравнить каждый баланс и ledger, старые Таро, free/paid snapshots, версии, платежи, возвраты, debt, HMAC сроки. Не публиковать строки/ID/ключи.
3. Дополнительно считать consent/pending персональными данными. До восстановления **выключить `ASTRA_DAILY_DELIVERY_ENABLED` у всех writers**, остановить доставку и дождаться завершения in-flight. Нельзя считать старый backup доказательством отсутствия позднего /stop или /delete.
4. Записать действующий deployment, SHA сборки, backup ID/UTC, bindings и имена параметров без секретных значений. Получить пригодную точку восстановления и определить, как будут сверяться события после неё.
5. Остановить writers совместимым maintenance Worker, как в TASK05; настоящий webhook и Cron settings не менять. Запретить другим Workers/admin writers писать в базу во время миграции; дождаться завершения in-flight. Снять свежую согласованную копию.

1. Workers & Pages → проверенный **тестовый** Worker → Edit code. Вставить весь `release/ASTRA_2_4_WORKER.js` как один ES module. SQL в JS не вставлять.
2. Сохранить действующие `DB`, токен, webhook/admin secrets, bot username и существующий `ASTRA_FORECAST_START_DAY`. Секреты в чат/репозиторий не передавать. `/activate` не открывать.
3. Проверить **`ASTRA_DAILY_DELIVERY_ENABLED=false`** (отсутствующий параметр тоже OFF), **`ASTRA_ECONOMY_V2_ENABLED=false`**, **`STARS_SHOP_ENABLED=false`**. SQL-флаги новой экономики/магазина также OFF. `ASTRA_FORECAST_COMPACT_START_DAY` и будущий policy start не назначать. Runtime 0028 оставить `delivery_quarantined=1`.
4. Deploy разрешается только отдельным решением владельца. В рамках TASK06 это не выполнялось. После будущей установки открыть `/health`: version `ASTRA-2.4-task06-rc`, schema_ready и consent_schema_ready/consent_gate_ready должны быть true при полной схеме; `broadcast_delivery_allowed=false`; blocker `delivery_quarantined` (после снятия карантина при OFF — `delivery_disabled`). `manual_content_ready` показывает готовность ручного пути отдельно. `ready=false`, `public_ready=false`, HTTP503 намеренны, не исправлять их откатом на старый JS.
5. При неполной/чужой схеме — `schema_not_ready` или `consent_gate_not_ready`, прогнозных HTTP нет. Рабочая базовая схема допускает ручные материалы, но ошибки DB нельзя игнорировать ради зелёного health.

## Ручной smoke без автоматической доставки

На собственных тестовых профилях: новый OFF; legacy ON без proof; Досье → Уведомления показывает цель/частоту/09:00–11:00 Москвы/отзыв. Отмена не подписывает. Подтверждение фиксирует proof; доставка всё ещё выключена. /stop отзывает; старая кнопка не включает; новый экран позволяет новое согласие. Проверить сообщение с истёкшей 15-минутной кнопкой, /delete и повторный /start без восстановленного согласия. Проверить нативные кнопки на телефоне, /privacy, шесть меню, старые покупки и цены 5/4; ранее оплаченные материалы открываются бесплатно.

Не приглашать старых ON к подтверждению автоматической личной рассылкой без отдельного правового основания. Доступный путь — добровольный вход человека в настройки.

## Отдельная будущая проверка доставки и Cloudflare Free

До снятия STOP-SHIP владелец отдельно разрешает испытание только своими добровольно подписанными staging-профилями и реальный контролируемый Telegram test environment. Это не разрешено данным заданием. Для отправок потребуются одновременно снятый runtime quarantine, env-флаг и действительное персональное proof; ни один флаг не обходит SQL eligibility.

Проверить реальные cold/warm CPU p50/p95/max и ошибки1102 при лимите10ms; D1 calls/statements, все HTTP subrequests, rows_read/rows_written, рост базы и суточные квоты. Проектный предел — 50 учитываемых операций, 500MB на одну D1. Проверить 8/20/100, разные знаки, cache conflict, две части, 403/429, timeout, DB outage, lease release, очередь не накапливает вечный retry. Локальный лимит46 внутренних +2 внешних =48 — модель и защитный потолок, **не измерение настоящего Cloudflare**. SQL-триггеры тоже потребляют CPU/rows.

Повторяющийся утренний Trigger для полного drain остаётся отдельным решением: рабочее окно 06:00–07:59 UTC, обычно09:00–11:00 Москвы; партия4, а не4за день. При одном запуске часть аудитории останется на ручном чтении. В TASK06 настоящий Trigger не менялся.

## Восстановление после сбоя и backup-consent

Предпочтительно совместимое исправление вперёд при maintenance. **Не возвращать Worker 2.3B, 2.4A или TASK01–05**: старый UI может менять ON без отзыва, старый код не реализует новый протокол; финансовые схемы0025/26 уже несовместимы с обычным rollback. Не удалять финансовые строки или снимать SQL guards.

Полный restore — только после решения владельца, с остановленными writers и env-доставкой OFF **до** восстановления. Проверить `delivery_quarantined=1` в восстановленной базе прежде, чем подключать совместимый Worker. Если backup был снят при quarantine=0, он не станет1 автоматически: оператор обязан установить карантин в изолированной копии при выключенной доставке. Затем сверить все /stop,/delete, новые оплаты/возвраты/бонусы после backup. Если достоверной истории отзывов нет, **не разрешать доставку по восстановленным proofs**. Держать карантин до согласованного прозрачного повторного opt-in с новой версией/инвалидацией старых прав; это отдельная операторская процедура, не скрытый массовый сброс в TASK06.

Старая копия может воскресить удалённый профиль или отозванное согласие; сама D1 не знает внешнюю историю. Автоматическая абсолютная защита от такого восстановления не обещается. Незавершённые Telegram HTTP также не отменяются. `unknown` не переотправлять автоматически, старые claims/last-day не чистить для «досыла».

Правовое основание подписки и HMAC, минимизация платёжных записей, ограниченный backup retention, реальные support/Terms, purge SLA и доступ к персональным копиям остаются решениями владельца. Новое согласие не является согласием на платежи или бонусный антиабуз. После smoke — повтор integrity, протокол проверок, flags OFF и карантин1. Только затем отдельное решение о следующем шаге.
