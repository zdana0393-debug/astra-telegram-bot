# Astra 2.3 editorial: подготовка проверки на тестовом боте

Это инструкция для владельца после редакционного ревью, не выполненный deploy. Codex не подключался к Cloudflare/D1/настоящему Telegram, не выполнял remote SQL, не менял webhook, Cron, секреты или production. Цель остаётся прежней: **astra-staging-21-worker**, binding **DB → astra-staging-21**, отдельный тестовый бот. Рабочую Astra 2.0 не выбирать.

1. Сравнить astra-2.3-editorial с astra-2.2-shell. Прочитать ASTRA_2_3_EDITORIAL_REVIEW.md и ASTRA_2_3_EDITORIAL_TEST_REPORT.md; проверить тексты, инженерную роль и честный ответ о реальных создателях. Сначала владелец утверждает стиль; полный движок гороскопа — отдельная задача.
2. Локальная полная проверка: `sh scripts/test-2.3-editorial.sh` на Node.js 22+ (в этой задаче проверено на 24.22.1). Нужны только существующие фикстуры SQLite, внешние сервисы и секреты не требуются.
3. Если владелец решит провести тестовую установку, сохранить активный JS/версию тестового Worker 2.2 для отката. Проверить имя **astra-staging-21-worker**, его существующий DB-binding и собственные тестовые переменные, включая Text BOT_USERNAME без @. Не присылать значения секретов и не заменять их production-значениями.
4. **SQL-миграций для этого этапа нет.** Не запускать 0021/0022 повторно ради редакционной версии, не импортировать production и не изменять данные D1. Предполагается уже рабочая полная схема 2.2. При её отсутствии прекратить установку: новый Worker намеренно оставляет прежнее schemaReady/503.
5. Только после отдельного решения владельца о тестовой установке: Cloudflare Dashboard → Workers & Pages → astra-staging-21-worker → Edit code. Полностью заменить JS файлом **release/ASTRA_2_3_EDITORIAL_WORKER.js**, не добавлять его к прежнему. Это самостоятельный ES module без npm/импортов/сборки. Публикацию на тестовый Worker выполняет владелец, не Codex в этом задании.
6. Сверить active deployment и `/health` тестового Worker: version=ASTRA-2.3-editorial-candidate, schema_ready=true, ready=true. Не вызывать /activate, setWebhook и не менять маршрут /telegram-webhook, secret header, binding или Cron. Существующий тестовый webhook продолжает принимать прежние обновления.
7. С телефона пройти /start, шесть направлений, «Назад»/«Главное меню», весь FAQ, методологию, команду, правила и помощь. Обычные страницы не должны объявлять себя вымыслом; FAQ о создателях должен честно объяснять редакционные роли, одного создателя и помощь ИИ. Сравнить страницу команды с обязательными функциями шести записей; первые четыре строки сохраняют скрытый код без подсказки.
8. Проверить бесплатный прогноз и число дня, карту дня, баланс и настройку рассылки. На новых тестовых операциях проверить старые суммы: старт 2, день +1, реферал +5, канал +5, расклад −3, секрет +5 один раз. Старые открытые кнопки и повтор подтверждения не создают второй оплаты. Если старый расклад был сохранён в 2.2, его прежний текст должен вернуться дословно; это ожидаемая совместимость.
9. Проверить пустые/недоступные разделы, /privacy и /delete на тестовом профиле. /delete действительно удаляет профиль — не использовать для этого реальные production-профили. Нет ни магазина Stars, ни новых платных услуг; отдельные планы не выдаются за работающие функции.
10. При редакционной ошибке можно вернуть сохранённый **release/ASTRA_2_2_WORKER.js** только тестового Worker: схема не менялась, денежные операции совместимы. Сохранённые новые расклады останутся в D1 и не переписываются откатом. При необъяснимом расхождении денег остановить тестирование и расследовать, не «чинить» баланс вручную. Не возвращать исходный Worker 2.0 поверх ledger-схемы.

В этой задаче подтверждена только локальная регрессия. Визуальная проверка на телефоне, реальный D1 и доставка Telegram относятся к последующей проверке владельца. Публикация/merge не выполняются автоматически.
