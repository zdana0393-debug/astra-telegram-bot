## Worker, ключ и прозрачное уведомление

Через Dashboard в будущем устанавливается только пересобранный `release/ASTRA_2_4_WORKER.js`; binding `DB` должен указывать на выбранную staging-базу. Сам Worker не включает flags. Никакие секреты этого задания не записаны и не запрошены; тесты используют явно синтетические строки.

При отсутствии ключа бонусы блокируются. `/health` возвращает 503 и безопасный `bonus_fence_blocker`, например `BONUS_FENCE_KEY_MISSING`, но `free_content_ready=true` при полной схеме и доступной D1. Бесплатное содержание и /delete продолжают работать. Это ожидаемый статус до настройки, а не готовность к публичному запуску.

До выдачи любых новых защищённых бонусов владелец должен принять опубликованный текст /privacy и исключение /delete, определить правовое основание и фактический график удаления/backup. HMAC — **персональная псевдонимизация**, не анонимизация. Здесь нет индивидуальной кнопки согласия: административное подтверждение отражает решение владельца, а не согласие каждого посетителя. Если выбранное правовое основание требует такого согласия, нужен отдельный согласованный интерфейс до активации.

После этого, только по отдельному решению владельца:

- В секретах Worker задать отдельно сгенерированный криптографически случайный `ASTRA_BONUS_FENCE_KEY` (минимум 32 байта; не пароль), публичный `ASTRA_BONUS_FENCE_KEY_ID`, например `v1`.
- `ASTRA_BONUS_FENCE_NOTICE_ACK=APPROVED_BONUS_FENCE_30_DAYS` задаётся только после реального принятия notice и основания.
- Вызовы защищённого admin API выполняются владельцем с прежним `Authorization: Bearer <ADMIN_KEY>`, без секретов в JSON/URL. Здесь приведены тела будущих запросов, они **не выполнялись**:

```json
{"action":"configure_key"}
{"action":"approve_notice","version":"bonus-fence-30d-v1","acknowledgement":"APPROVED_BONUS_FENCE_30_DAYS"}
{"action":"status"}
{"action":"bootstrap"}
{"action":"purge"}
```

Путь: `POST /internal/economy/fence`. `bootstrap` обрабатывает одного прежнего пользователя и максимум пять ledger-строк за вызов. Повторять до `remaining=0`, оставаясь в maintenance. Переносятся только наблюдаемые реальные выплаты за последние 30 дней, с исходным временем; opening не считается наградой. Это не начисляет денег. Ключ/notice/config не возвращают значения секретов или псевдонимы пользователей.

Если не перенесённые старые права удаляются без пригодного ключа, профиль всё равно стирается. Вместо сохранения Telegram ID устанавливается **общая неперсональная пауза бонусов до 30 дней** (`BONUS_FENCE_SEED_QUARANTINE`). Это намеренно консервативная защита; не обходить её сбросом времени. Завершение bootstrap до возобновления writers предотвращает штатное попадание в этот сценарий.

## Очистка, ротация и восстановление

Срок eligibility — ровно 2 592 000 секунд после фактической выплаты, не календарный месяц. Попытки и повторные регистрации срок не продлевают. В живом профиле однократные claims продолжают запрещать повтор и после TTL. После /delete остаются только минимальные права без исходных ID/имён/текстов и отдельно прежние необходимые платёжные доказательства/долги.

Просроченные fence-строки удаляются порциями до 200: перед обработкой private updates, через защищённый `purge` и при уже существующем scheduled-вызове. Получатели, часы и алгоритм рассылки не менялись. Это **не нативный TTL D1 и не обещание физического удаления секунда в секунду**. Оставшаяся просрочка даёт `BONUS_FENCE_PURGE_PENDING` и блокирует бонусы, пока очередь не очищена. Владелец обязан измерить объём и частоту очистки, задать проверяемый максимальный срок физического удаления и алерт. Один запуск в сутки при большом потоке может быть недостаточен. Правило хранения/правовое основание должно учитывать этот интервал; если нужен жёсткий физический максимум 30 суток, активация блокируется до решения расписания в отдельно разрешённом этапе.

При ротации использовать новый ID. Прежние необходимые ключи хранятся в отдельном секрете `ASTRA_BONUS_FENCE_PREVIOUS_KEYS` — JSON map `старый_id → старый_ключ` (не публиковать в чате/репозитории). Максимум три предыдущих ключа. Пока есть живые права старого ключа, убрать его нельзя. Смена секрета при прежнем ID даёт `BONUS_FENCE_KEY_CHANGED`; потеря необходимого предыдущего ключа — `BONUS_FENCE_PREVIOUS_KEYS_REQUIRED`. Не удалять registry/права для устранения blocker. Сначала сменить конфигурацию при паузе, затем `configure_key`, затем проверить повторную регистрацию и /health. Удаление старого ключа допустимо только после истечения всех его прав, очистки и проверки политики резервных копий. Не ротировать быстрее вместимости ring.

Backup тоже содержит персональные права. Утвердить доступ, шифрование, конечный срок хранения и удаление копий. Восстановление: writers OFF → правильный набор ключей → очистка по **текущему** UTC, без изменения awarded_at/expiry → сверка ledger/прав/оплат → bootstrap при необходимости → smoke. Старый backup может не содержать позднее начисленные права и платежи: сначала восстановить события из доступных доказательств и сверить Telegram штатным способом, не обещать отсутствие повторов при утрате истории. Restore не должен молча «воскресить» удалённые профили.

## Будущее включение и исправление

Оба флага остаются OFF в этом задании. После последующих этапов и ревью владелец выбирает будущую московскую дату. Защищённый `/internal/economy/policy` принимает `arm` только при runtime-флаге ON, настроенном key/notice, отсутствии bootstrap backlog и будущей дате. Эти действия в текущей работе не выполнялись. До даты — прежние номинальные награды с защитой; после — новые; старые pending договоры +5 сохраняются.

Новые покупки Таро за 5 начинают применяться в patched Worker независимо от будущего бонусного cutover; старые кнопки за 3 лишь читают уже оплаченный результат или запрашивают новое подтверждение за 5. Stars-магазин остаётся закрыт. Новые цены 40/110/240 не меняют ранее созданные 100/270/570: поздние платежи/возвраты используют снимок заказа.

Проверки staging до публичного использования: реальное D1 поведение триггеров, race/retry/fault, Cloudflare CPU cold/warm и ошибки 1102, обе цифры D1 API calls и SQL statements, rows_read/rows_written, рост базы до 500 МБ, 50 запросов на invocation. Локальные wall_ms не доказывают лимит CPU 10 мс. При отдельном разрешении Stars — только dedicated Telegram test environment и реальная проверка getChatMember с правами администратора. Реальные счета здесь не выставлялись.

**После 0026 обычный откат старым Worker недопустим.** Старая схема уже заменена и его readiness отвергает базу. Безопасное исправление: maintenance + оба flags OFF → сверка доказательств/ledger → исправленный Worker, совместимый с 0026, либо новая явная миграция. Полный restore допустим только после отдельного решения и учёта всех событий после backup; иначе теряются оплаченные права и появляются повторные выплаты. Не сбрасывать balances, долги, ключи, pending платежи или webhook ради отката.
