## 3. Переход политики и старые пользователи
Новая переменная ASTRA_ECONOMY_V2_START_DAY = YYYY-MM-DD Europe/Moscow либо эквивалентная зафиксированная в D1 дата политики (чёткий порядок приоритета). Активация с будущей московской даты; до неё действуют старые +2/+1/+5, после неё только новые суммы для новых событий. Подготовленная схема должна быть полной для /health; любой partial migration => 503, не молчаливый запуск. Предусмотреть отдельный стоп-флаг ASTRA_ECONOMY_V2_ENABLED = false до ручного разрешения.

Нельзя задним числом пересчитывать старый opening, баланс, старые бонусы, GPT6 или покупки. Реферал, уже получивший старые +5, не получает +14 повторно. Подписчик с channel_rewarded=1 не получает +8. Старые приглашения с сохранённым referrer_id и незавершённым выбором знака до cutover должны быть помечены как legacy-pending, для них при последующем выборе знака действует исходный договор +5 пригласившему, не создаётся второй новый реферальный договор. До применения migration 0025 зафиксировать их количество. Новым приглашённым после cutover — новый договор со статусами pending/eligible/paid, без старого мгновенного +5, при активности в две разные даты платятся +14/+4 атомарно. Не превращать старое referral_rewarded=1 в подтверждение двух дней у новых участников. Удалённый реферер — чётко определённое безвредное поведение и публичные правила, без тихого создания балансов.

Техническая коллизия: astrа_referral — прежний SQL-trigger начисляющий +5 сразу при UPDATE zodiac, astra_operations имеет CHECK для daily=+1, channel/referral=+5, tarot=-3; оба существуют в 0021. Ни один новый grant +3/+8/+12/+14 не проводить через поддельный reason='tarot' или UPDATE balance без синхронной ledger-проводки. Требуется **отдельная корректная 0025**: продуманный DROP/CREATE версии legacy-referral trigger в короткой writer-pause и rollback-aware release, новые таблицы claims/контрактов, SQL-триггеры для атомарного изменения баланса+ledger или доказанный эквивалент. Прежние записи не изменять. Обычная JS-проверка SELECT before INSERT недостаточна при гонке.

При переключении отключить возможность старой '+1 вручную' и '+5 за канал' на новом дне через устаревшие callbacks — новые SQL guards обязаны предотвратить двойное списание/начисление, новые кнопки объясняют автоматически полученный +3 и статус канала +8. Проверить old Worker rollback ПОСЛЕ смены правил: нельзя просто возвращать 2.4A JS, если он думает, что действуют старые суммы! Требуется отдельный безопасный maintenance/rollback режим или неизменное совместимое поведение, доказанное тестами. При откате данные пользователей и оплаты не терять.

Механизм начисления за первый активный день должен переживать: already existing activity row на дату cutover, ретрай Telegram update, разные update_id, ошибку Telegram после записи и гонку нескольких запросов. Не создавать ложную активность от Cron, service messages, pre_checkout, payment refunds. Награды и миллисекундные события сохраняются через immutable claim IDs, не по обновлению поля streak без ledger. Для одинакового дня действует одна запись. 3/7/30 важны по реальным датам: серии не должны искусственно восстанавливаться после ошибки доставки, пропуски не отнимают полученную пыль.

## 4. Stars — цены, только кандидат, магазин по умолчанию ВЫКЛЮЧЕН
Три товарных пакета (владелец окончательно подтверждает перед активацией):
- 10 XTR => 100 ✨
- 25 XTR => 270 ✨
- 50 XTR => 570 ✨
Отдельного вывода пыли в деньги, обмена между пользователями, продажи изображений или подписок в этой версии нет. В UI чёткая цена и amount перед инвойсом, подтверждение согласия с Terms, отсутствуют скрытые платежи и искусственная срочность.

STARS_SHOP_ENABLED = false по умолчанию. Не выставлять счёт ни по одному пути при отключённом флаге; любые старые callback_data со стоимостью после отключения => без инвойса. Ещё один флаг окружения ASTRA_TELEGRAM_TEST_MODE; реальная XTR-оплата допускается только после явного подтверждения владельца, корректного Bot API endpoint, проверки test environment и поддержки, а не от одного флага. Обычный 'staging' бот в обычном Telegram всё равно может выставить настоящий Stars invoice! Никогда не считай просто названием test-бота оплату безопасной.

Официальные документы на 07.11.2026: https://core.telegram.org/bots/payments-stars, https://core.telegram.org/bots/api, https://core.telegram.org/bots/features. Telegram Stars для цифровых товаров: currency='XTR', prices=[{label,amount}] (ровно одна цена), provider_token отсутствует или пустой согласно текущей документации. Стадии: sendInvoice -> Update.pre_checkout_query -> answerPreCheckoutQuery (не позднее 10 секунд) -> Update.message.successful_payment -> только ПОСЛЕ неё atomic credit + ledger -> квитанция/поддержка. Не выдавать награду по click, sendInvoice, precheckout, receipt without successful_payment, fake callback.

## 5. Orders, charges, retry, privacy
Новая таблица payment orders с уникальным непредсказуемым ID/payload, telegram_id (owner), кодом пакета, ценой XTR, количеством пыли, статусом, timestamps и server-side snapshot цены. Следующая таблица payment events/receipts с UNIQUE telegram_payment_charge_id и FK на заказ. Никаких чужих профилей и доверия к client-provided amount/payload; валидировать currency, amount, identity, order, allowed statuses и отсутствие повторной charge. Invoice_payload длиной <=128 bytes, user_id не должен быть тайной/аутентификацией: доверять authenticated update & server order. Только private chat.

Paid acknowledgement: first save proof+claim+balance/ledger in one D1/SQLite atomic statement/trigger with UNIQUE charge ID, так что при double webhook/2 различных update_id/concurrent connections/Telegram retry начислить ровно один раз. Если Telegram sendMessage/receipt даст ошибку, повторно открыть историю и подтверждённый платёж без нового credit.

Состояния created, invoiced, confirmed, credited, refund_requested/refund_in_progress/refunded, needs_review; не говорить, что внешняя API операция и D1 транзакция атомарны. Платёж, успешный в Telegram, но временно не записанный в D1, должен иметь путь восстановления: повторный update/сверка getStarTransactions и операторский журнал. Нельзя терять оплаченные товары из-за 14-day cleanup update jobs.

Для /delete и privacy: открыто описать, какие платёжные идентификаторы Telegram нужны для refund/споров, кто и сколько хранит; не обещать полное удаление оплаченных финансовых записей, если они остаются. Без отдельного утверждения retention/поддержки и возможностей удаления — коммерческий флаг должен оставаться disabled. Никаких секретных несогласованных списков Telegram ID и shadow антифрод-следов.

## 6. Refunds: безопасность при уже потраченной пыли
Команда /paysupport и /terms обязательны; /support — желательно. Нужен реальный, но конфигурируемый контакт владельца (не выдумывать адрес), понятная политика возвратов и условий доступа. Для оператора — безопасная процедура refundStarPayment(user_id,telegram_payment_charge_id), только после admin-auth, с журналом и статусом.

РЕАЛЬНАЯ ПРОБЛЕМА: часть начисленной за Stars пыли может быть уже потрачена, а текущий баланс CHECK(balance>=0). Нельзя отрицать факт возврата, бесследно оставить полное вознаграждение, удалить купленные интерпретации или допустить отрицательный баланс. Выбрать и доказать один прозрачный сценарий:
A) при реальном refund уменьшить доступный баланс на min(current_balance, purchased_dust), остаток отразить в явном refund_debt; будущие новые начисления направлять на погашение долга до пополнения доступной пыли, не переписывая старые покупки; показать это в Terms/поддержке; либо
B) отдельный, согласованный с владельцем режим ручной компенсации, полностью блокирующий автоматический refund до корректной операции. Вариант B означает коммерческий запуск ЗАПРЕЩЁН до устранения.
Любая реализация долгов должна быть документирована, проверяема в ledger, устойчивой при гонках с existing Tarot -3/forecast -4 и бонусами. Refund внешним API и запись компенсации в D1 требуют crash recovery, двойной refund/двойное списание недопустимы. При возврате не отнимать уже выданные предсказания задним числом, не делать тексты недоступными. При оплате частично начисленного пакета и /delete нельзя создавать отрицательный balance. Обработка message.refunded_payment и reconciliation через getStarTransactions обязательны либо должны быть явно обозначены как release-blocker для реальной торговли.

Если Codex не сможет доказать корректность полной refund/debt схемы в этой же ветке, НЕ утверждать 'готово к реальным Stars', оставить магазин отключённым и отчёт release blocker. Основную 2.4 без продаж можно тестировать, но production-магазин по этому контракту нельзя запускать.

## 7. Integrity and validation
Новые суммы проходят отдельные idempotent reward_claims и wallet_ledger; баланс равен SUM(ledger.delta) для каждого НЕ удалённого профиля; все новые проводки имеют обоснованную reason и версию политики; никаких потерянных pending payments / refunds. Дата Moscow 23:59/00:00, leap/year, DST нет, повтор webhook после полуночи не меняет дату первоначальной операции. Двойные referral (две даты) и два подтверждения подписки не создают двойных наград. После 7/30/90 дней нет неконтролируемой инфляции, составить точную симуляцию.

Нужно минимум: 2.0→2.4A full regression, дополнительный набор 2.4B, 20+ конкурентных SQLite connections по каждому типу кредита/purchase/refund, fake Telegram 400/403/429/5xx/timeouts, тест invoice/pre_checkout до 10s, malformed/forged payload, wrong currency/amount/user, forwarded invoice, duplicate charge ID с разными заказами, сервисное refunded_payment, idempotent SQL, rollback при ошибке ledger, /delete FK ON/OFF, partial migration/schemaReady, ненадёжная сеть, reserved/cutover, old callbacks. Измерить CPU/quotas и дополнительные D1 записи; тесты Node не равно Cloudflare реальной D1. Браузерный JS на Workers Free 10 ms CPU per HTTP/Cron: оценить cold/warm, не заявлять production-ready без реальных замеров.
