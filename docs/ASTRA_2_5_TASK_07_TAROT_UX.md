# TASK07 — самостоятельные вопросы и защита результата

Локальный кандидат; новые продажи и сбор вопросов выключены. Проектные цены прежние: basic3=5, тематические3=8,5=14,7=21,10=32 ✨. Энциклопедия3.0 с прежними8/10/16/24/38 не переопределяет их. Бесплатная карта дня и старый расклад5 не менялись.

## Пользовательский путь

Таро → «Новый вопрос» → одна из пяти тем → подходящий формат → необязательный вопрос → экран цены/баланса/позиций → явное подтверждение → текст → история. Финансы используют basic3 за5 или общие5/7/10; отдельного придуманного тарифа «финансовый3 за8» нет. Тематические отношения/работа/выбор имеют собственные три позиции за8; basic3 тоже доступен в каждой теме.

«Текущий заказ» возвращает последний действующий заказ. «Новый вопрос» открывает выбор для нового намерения. Форматная кнопка содержит случайный идентификатор намерения, а не ключ spread/theme. Повтор этой же кнопки возвращает исходный заказ; другая тема/формат не подменяет его молча. Для следующего самостоятельного вопроса нужно снова нажать «Новый вопрос». Два одинаковых вопроса — разные покупки, если человек явно начал новый заказ. Карты могут случайно совпасть: гарантировать неповторимость случайных раскладов между покупками нельзя.

Подписи `q7:` включают96-битный HMAC, владельца, generation, message_id, действие, payload и expiry. UUID упакован в22 base64url знака; это публичный ID заказа, не seed. Подпись предыдущего профиля/другого сообщения/чужого пользователя не проходит. Telegram update_id и request_key закрепляются в SQL receipts. После очистки старый запрос получает отказ, а не новый draw. Receipts живут с профилем, удаляются при /delete.

История содержит только оплаченные результаты, включая прежние3/5. Новые строки не переписывают старые тексты. Результат открывается бесплатно даже при OFF всех новых флагов; читатель V1 не зависит от текущей редакции. Ручное чтение — до трёх частей за страницу с паузой5с; неизвестная доставка требует отдельного согласия на возможный дубль. Новый оплаченный заказ отправляется прежним lease-адаптером, а не через лимит ручного чтения. При403/429/сети сохраняется покупка; новый draw/дебит не выполняются.

## A/B: момент формирования текста

|Схема|Безопасность денег|Неоплаченное хранение|Недостаток|
|---|---|---|---|
|A: sealed до выбора оплаты, TASK06|Хорошо проверенная: snapshot до debit|Два больших текста на каждое предложение|Просмотр каталога расходует квоту/CPU/место; слияние тем мешает разным вопросам|
|B: debit, затем генерация|Требует отдельной финансовой компенсации и durable workflow|Компактно до оплаты|Окно «деньги списаны, результата нет»; не выбрано|
|Выбранный гибрид: компактное намерение → подтверждение → sealed → прежняя атомарная покупка|Нет debit до durable sealed; debit+ledger+paid одной SQL-операцией|UUID+настройки+256-битный seed; большой текст только после явного подтверждения|Есть короткая lease и возможность sealed unpaid при гонке за баланс/ошибке D1|

Seed создаётся Web Crypto один раз. HMAC-SHA256 с доменом draw:v2 даёт воспроизводимый поток для прежнего Fisher–Yates и отдельной ориентации. Тема/личный вопрос не меняют draw. При перезапуске используются тот же seed и исходный UTC timestamp, поэтому повтор даёт те же байты. После sealed читается только сохранённый результат. После paid никакая новая редакция не пересчитывает snapshot. Потеря ответа после debit проверена SIGKILL и искусственными D1-сбоями.

Lease30с защищает генерацию от конкурентов; срок намерения900с не продлевается при позднем seal. CHECK offers29.created_at+900 остаётся прежним, а новый purchase-guard дополнительно проверяет первоначальный expiry намерения. Достаточность баланса проверяется при lease и окончательно в старом SQL purchase guard. Нет отдельного debit до записи paid, следовательно генерационная компенсация не нужна. Telegram-возвраты Stars остаются отдельным старым механизмом.

До оплаты DTO/история/экран/callback/HTTP не возвращают cards, reversed, seed, result или snapshot. Даже уже sealed unpaid после сбоя доступен только внутреннему адаптеру. Владельцы с прямым административным доступом к D1 видят данные: это не шифрование от администратора.

## Ограничения и хранение

Суточного бизнес-лимита оплаченных раскладов нет. SQL ограничивает одновременно открытые неоплаченные намерения: default5, настройка1…20. Default20 новых неоплаченных запросов за минутное окно, настройка4…100, — техническая защита от перебора. Оплата освобождает единицу своего burst-окна; отмена её не возвращает. Проверены16 покупок за одну дату, четыре самостоятельных заказа и1000 попыток unpaid. Это не защита от множества разных Telegram-аккаунтов.

Soft cap350000000 байт и retention900+86400с по умолчанию остаются из0030. Большой sealed stock до истечения срока не удаляется. Очистка явно запускается только отдельным локальным harness, не webhook/Cron/HTTP. На один token≤20 offers+quota+intents+старых burst-строк суммарно. Две фазы имеют независимые атомарные SQL-границы и тот же durable token; повтор после сбоя продолжает незавершённую фазу. Это не одна общая транзакция двух фаз. Paid/ledger не удаляются. Compact receipts остаются до /delete; их рост учтён отдельно.

Дневная квота0030 больше не расходуется новыми намерениями; старая таблица и прежние доказательства не переписываются. Старые просроченные квоты доступны прежней очистке. Технический burst содержит Telegram ID только при живом профиле, удаляется с ним; новые бессрочные HMAC-регистры не вводятся. Бонусный HMAC30 дней не менялся.

## Добровольный личный вопрос

Отдельные env `ASTRA_TAROT25_QUESTIONS_TEST_MODE` и SQL31.questions_enabled defaultOFF. Даже при их включении требуется пользовательская кнопка согласия. Без текста доступно полноценное чтение по теме. Хранятся версия политики, UTC-время, update и message_id согласия; при покупке доказательство включается в неизменяемый snapshot. Ввод — одно сообщение до500 UTF-16 знаков и500 codepoints, до2000 UTF8 байт. NFC/пробелы нормализуются, управляющие/биди-символы удаляются, некорректные суррогаты отклоняются. SQL параметризован, Telegram parse_mode не используется. Ни LLM, ни исполнения инструкций из вопроса нет.

Не просим имён, адресов, телефонов, здоровья и данных третьих лиц. Простые контактные/чувствительные шаблоны отклоняются без сохранения; это не безошибочная DLP и не распознавание всех персональных сведений. /команды, меню и GPT6 не захватываются. Только один незаполненный consent-поток на профиль; гонка двух ответов сохраняет одно значение. После заполнения вопрос не перезаписывается. Отзыв отменяет неоплаченный заказ и сразу удаляет личный текст; старая кнопка согласия не оживляет заказ. Новый вопрос требует нового намерения.

Оплаченный вопрос хранится с paid до /delete; unpaid — до expiry+retention с фактическим удалением при отдельном cleanup. Без работающего cleanup физическое удаление задерживается; экран это прямо сообщает. Гарантированный SLA и правовое основание должен утвердить владелец до реального сбора. /delete удаляет вопросы/seed/receipts текущего профиля; прежние исключения для платёжных доказательств остаются в политике2.4.
