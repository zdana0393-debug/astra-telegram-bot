## Бюджет и ограничения

Для семи обычных покупок с альбомом наблюдались26–27 SQL statements +5–6 HTTP =31–33 консервативных операции. Long58k —35 SQL +12 HTTP =47, неполная доставка текста закрывает отправку альбома. Картинки добавляют до одного ownership SELECT и одного HTTP; прежний runtime guard резервирует завершающие операции и откладывает медиа при нехватке бюджета. Отдельные фото/большой альбом не отправляются78 запросами на каждом раскладе. В D1 не сохраняются image blobs, фото-очередь и новые неоплаченные записи.

Пример с синтетическим реестром: исходный TASK072019722B/raw и340386B/gzip9; частная сборка2044952B/raw и345024B/gzip9. Это **не сборка с реальным Telegram-реестром** и не метрики upload/startup/CPU Cloudflare. Настоящие CPU/1102/rows_read/rows_written/subrequests и ограничения Telegram по альбомам/частоте — NOT_TESTED. Связанные квоты одного Cloudflare-аккаунта остаются общими.

Фото-доставка не имеет отдельного долговечного журнала и exactly-once гарантии. При обрыве после приёма Telegram возможен дубль при явно запрошенном повторном чтении; повторной оплаты нет. Простой text fallback сохраняется. `protect_content` не защищает от скриншотов, Telegram бот-чаты не end-to-end encrypted; отправленное лицо будет видно получателю. Качество реальных изображений/подписей/ориентации ещё требует визуальной приёмки.
