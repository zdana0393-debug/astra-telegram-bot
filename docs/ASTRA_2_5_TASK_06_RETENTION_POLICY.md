# Astra 2.5 TASK06 — предварительная политика хранения

**Разрешено только локальное испытание на фиктивных данных. Для реального сервиса эта политика не утверждена.** Новая миграция0030 и TASK06 Worker сохраняют STOP-SHIP. Новые продажи, очистка, экономика, Stars и уведомления по умолчанию OFF. Старые SQL0021–0029 и compatibility v1 не менялись.

## Настройки и права

| Параметр | Локальное значение по умолчанию | Где задаётся |
|---|---:|---|
| TTL оплаты |900с, без изменений|CHECK0029; не меняется этой задачей|
| Дополнительное хранение unpaid после expiry |86400с (24ч)|`astra_tarot30_policy.retention_seconds`, целое3600…2592000|
| Новые предложения за московские сутки |3|`daily_limit`, целое1…10000|
| Максимум строк offers+quota за один запуск очистки |20|`batch_limit`, целое1…20|
| Soft cap |350000000 байт|`soft_cap_bytes`, целое1048576…450000000|
| Допуск новых draft |0|SQL `write_enabled` и env `ASTRA_TAROT25_STORAGE_TEST_MODE`|
| Допуск очистки |0|SQL `cleanup_enabled` и тот же env test-mode|

Обычный RWS-флаг `ASTRA_TAROT25_ENABLED` и SQL runtime29.enabled тоже обязательны для новых покупок. Флаг storage-test сам ничего не продаёт и не включает Cron. Ранее оплаченное читается при выключенных новых флагах. Срок/лимиты/soft cap меняются только с закрытыми storage gates и увеличением `revision`; старые paid snapshots не зависят от этих значений.

TTL900с не является retention. До наступления `expires_at+retention_seconds` unpaid не удаляется, включая отменённый заказ. Политика хранения относится к текстам неоплаченных предложений, а не к платёжным доказательствам или истории купленного.

## Создание, повтор и суточный лимит

Повтор того же request_key/update_id возвращает прежнее предложение. Новый запрос того же формата/темы использует уже действующий **неоплаченный** snapshot текущего владельца/generation, ревизии и версии цены. Он не перетасовывает карты, не продлевает900с и не тратит ещё одну единицу лимита. По каждому alias остаётся компактное доказательство запроса, поэтому его поздний повтор после purge получает `OFFER_PURGED`, а не новый draw.

При создании нового snapshot SQL проверяет владельца/generation, флаги, отсутствие прежнего request/update и актуальную дневную квоту. После INSERT он атомарно увеличивает счётчик и фиксирует receipt. Отмена, expiry, очистка и покупка не возвращают квоту. Предварительная проверка до генерации сокращает лишние вычисления, но окончательное решение принимает SQL. Конкуренция не защищается JS mutex.

Ревизия каталога также существенна: после OFF→ON прежнее unpaid может ещё не истечь по времени, но уже не подходит для оплаты. Оно не переиспользуется как действительное. Повтор старого запроса/подтверждения объясняет изменение настроек; новое меню создаёт новый quote в пределах квоты. Уже оплаченный материал открывается дословно и бесплатно.

## /delete и дневные HMAC

Для защиты от сброса квоты повторной регистрацией используется **новый отдельный** HMAC-домен `astra:tarot:unpaid-quota:v1`, Telegram ID и московская дата; ключ — имеющийся webhook secret. Бонусный HMAC30дней не изменялся. Никакой новый секрет не запрашивается.

Пока профиль существует, таблицы bindings/requests содержат его Telegram ID и generation. `/delete` удаляет их, snapshots и обычную историю по прежним правилам. В независимой дневной quota остаются только дата, HMAC и использованный лимит. Это **псевдонимизированные данные, не обезличивание**: держатель ключа способен проверить предполагаемый ID. Метка действует только для своей московской даты. Просроченная строка становится доступной отдельной ограниченной очистке; сама смена суток не гарантирует физического DELETE.

В тестовом каталоге и `/privacy` при включённом test-mode дано дополнительное объяснение. При OFF прежняя privacy-выдача не меняется. До реального включения владелец должен утвердить это исключение, его notice/основание, расписание и предельную задержку физического удаления. Без работающего cleanup строки технически сохраняются дольше своей пригодности. Текущий релиз не обещает hard-delete в полночь.

Отпечаток ключа фиксируется один на дату без ID пользователя; смена ключа в эти сутки закрывает новые admission, вместо нового счётчика. Совпадающий Telegram ID после регистрации получает другую generation, но тот же дневной HMAC и прежний расход. Это не защита от множества разных Telegram-аккаунтов.

## Проверяемая SQL-процедура очистки

`cleanup30` принимает заранее выбранный caller token32hex и лимит. Единственный INSERT в `astra_tarot30_cleanup_runs` запускает триггерную процедуру:

1. Проверяется завершённость0030, разрешение cleanup, ревизия, retention, время и целочисленный лимит≤20.
2. Выбираются самые старые eligible offers: expiry+retention прошли, профиль существует, generation совпадает, покупки и ledger-следа по offer_id нет.
3. Внутри этой же операции выдаются краткоживущие claims. При DELETE заново проверяются владелец, generation, неизменяемые даты/status, текущая ревизия/разрешение и отсутствие paid/ledger.
4. Удаляются только эти unpaid строки. Считаются агрегаты количества и UTF8 payload; claims удаляются.
5. Оставшийся бюджет строки используется для старых дневных quota. Сумма offers+quota≤20. Текущую квоту удалить нельзя.
6. Run завершается. Claims после успешной операции пусты. Audit хранит только token, параметры, время и количества/байты; без ID, вопроса или текста.

NULL token, дробные настройки и подмена параметров отклоняются. Прямой DELETE unpaid живого профиля вне процедуры запрещён; DELETE paid запрещён даже с включённой очисткой и FK OFF. FK ON дополнительно защищает связь purchases→offers. Обычный `/delete` остаётся явным исключением удаления всего профиля по прежней политике.

SQL INSERT и все его триггеры атомарны в локальном SQLite. До COMMIT сбой откатывает batch целиком. После COMMIT неизвестный ответ восстанавливается **тем же token**: возвращается прежний агрегат, следующая партия не удаляется. Нельзя после неизвестного исхода выдавать новый случайный token как «повтор». Реальную D1 атомарность/лимиты ещё предстоит проверить отдельно.

`preview30` ничего не меняет: показывает общее eligible количество/UTF8 payload и ближайшую партию. Это оценка логического удаления данных, не обещание уменьшить физический файл или D1 billing.

## Soft cap и расходы

При admission SQL использует локально проверенные table-valued PRAGMA page_count/page_size. К текущему allocated размеру добавляется запас двух payload и65536 байт; для alias предусмотрен запас8192 байт. Это консервативный порог новых предложений, **не точная модель D1**, не глобальная резервация всех будущих оплат и не запрет внешним writers увеличивать базу. Если PRAGMA не поддержаны D1, новые записи должны отказать, без небезопасного обхода; saved reads не требуют этих PRAGMA.

Оплата существующего quote сохраняет прежние атомарные guarantees: при невозможности записать snapshot нет отдельного списания. Нужен мониторинг общего размера, остальных сервисов и будущих paid copies. SQLite DELETE обычно освобождает страницы для reuse, не уменьшает файл. Legacy stock, уже превышающий soft cap, после очистки может оставаться закрытым для новых admission. Не повышать порог наугад и не запускать VACUUM на действующей базе. Требуется отдельно испытанный перенос в новую компактную копию с сохранением rowid/sequence, ledger и paid hashes.

Компактные request receipts нужны весь срок жизни профиля, а не24ч: иначе поздняя старая кнопка снова создаст заказ. Days/key fingerprints и cleanup aggregates не содержат ID; их рост также учитывается в аудите. TASK06 не добавляет разрушительную очистку этих доказательств. Расписание cleanup не подключено ни к Telegram webhook, ни к существующему scheduled/Cron.

## Удобство и решения владельца

Три новых предложения могут оказаться слишком жёсткими для семи форматов: выбор ещё до оплаты создаёт draw и расходует квоту. Повтор текущего формата бесплатен по квоте, но попробовать все семь за сутки с default3 нельзя. Отдельный локальный тест доказывает возможность настройки7; **default3 не заменён**.

На утверждение: retention24ч после expiry; rate3 либо рекомендуемый для обсуждения7/сутки; soft cap350000000 байт; batch20; отдельный, измеренный режим очистки и SLA просроченных HMAC; условия хранения компактных receipts и aggregate logs. Альтернатива UI с просмотром описания без подготовки draw требует отдельного решения и здесь не реализована. Пока решений и реальной платформенной приёмки нет — OFF и STOP-SHIP.

SQL completion разделён на7 guards, чтобы каждый statement укладывался в консервативные50КБ (максимум28413 байт). Все223 core определения и primary completion продолжают сравниваться буквально; bodies всех частей дополнительно проверяются полным JS/native manifest. Отметка migration_done сама по себе никогда не доказывает корректную схему.
