# Astra 2.4: платежи, поддержка и восстановление

7 ноября 2026, Europe/Moscow. Инструкция для будущего ручного использования **после отдельного разрешения владельца**. Во время разработки выполнялись только mocks/локальный SQLite: никаких getMe к ботам, счетов, возвратов или D1-запросов.

## Условия допуска

Магазин закрыт по умолчанию. Нужны одновременно `STARS_SHOP_ENABLED=true`, D1 `stars_enabled=1`, согласованная конфигурация поддержки/Terms/хранения, закреплённый bot ID и отдельное разрешение окружения. Бонусы управляются независимо.

Обычный staging-бот в обычном Telegram способен выставить **настоящий** счёт XTR. Для тестов необходимы выделенные бот, аккаунты и токен в dedicated Telegram test environment, отдельная база и endpoint `/bot<TOKEN>/test/<method>`. Проверить действующую официальную документацию и реальную принадлежность окружения. Имя бота не подтверждает безопасность оплаты. Ветка не содержит токенов/контакта владельца. `support@example.test` встречается только в тестовых fixtures и сгенерированных примерах.

- `/terms`: цена/согласие, внутренний характер пыли, возврат и долг, хранение.
- `/payments` / «Мои платежи»: только свои заказы, 12 строк, Старее/Новее/Обновить.
- `/paysupport` / `/support`: настроенный контакт и инструкции обращения.
- `/privacy`: оплаченные доказательства и долги сохраняются после /delete открыто, без обещания полного стирания.

Владелец должен отдельно утвердить цены **10 XTR → 100 ✨, 25 → 270, 50 → 570**, юридически приемлемый текст Terms, реальный контакт, срок и основания хранения. Код допускает 180–3650 дней; 365 в fixtures — пример, не утверждённый срок. Не активировать коммерцию до этого решения.

## Состояния и доказательства

`created → invoiced → confirmed → credited`: заказ, отправка счёта, pre_checkout, сохранённая оплата. Пыль появляется только при authenticated `successful_payment` или восстановленном эквивалентном доказательстве `getStarTransactions`, никогда по кнопке/pre_checkout. Snapshot заказа содержит пакет, XTR, пыль, scope, версию цены/Terms. Payload — UUID, не идентификатор пользователя. Счёт имеет одну XTR-цену и пустой provider_token.

Отправка счёта защищена SQL lease. `delivery=unknown/sending` не повторяется автоматически: сначала проверить Telegram. Заказ технически истекает для нового pre_checkout спустя 24 часа, это не маркетинговая срочность; подтверждённая поздняя оплата всё равно учитывается. Бюджет pre_checkout от входа HTTP: 6 секунд на schemaReady и проверку заказа + 2,5 секунды API; реальную задержку необходимо измерить.

Receipt, уникальный charge ID/hash, баланс, ledger и погашение долга фиксируются одним SQL statement с триггерами. Сбой квитанции не повторяет кредит. Другая реальная charge для одного заказа, чужой плательщик, неизвестный payload или несовпадающая сумма сохраняются `needs_review`, без автоматического кредита. При удалённом профиле он не создаётся оплатой автоматически.

Состояния возврата имеют долговечную request-запись `requested/in_progress/needs_review/refunded`; заказ отражает `refund_in_progress/refunded/needs_review`. Lease и audit хранятся независимо от 14-дневной очистки jobs. API и D1 **не являются одной транзакцией**.

## Операторский доступ

Все маршруты ниже — POST, JSON, `Authorization: Bearer <существующий ASTRA_ADMIN_KEY>`, полная схема 0021–0025. Не передавать admin key в URL, чат, тикет или screenshots. Секреты вводятся владельцем локально; Codex их не запрашивает. Ответы status — `Cache-Control: no-store`.

| Маршрут | Тело JSON | Назначение |
|---|---|---|
| `/internal/payments/status` | `{"order_id":"UUID"}` | Свой операторский просмотр заказа, payer, charge, credited_dust |
| тот же | `{"charge_prefix":"12–64 hex символа из номера обращения"}` | До 5 аномалий; уточнить при неоднозначности |
| `/internal/payments/refund` | `{"charge_id":"проверенный telegram_payment_charge_id"}` | Durable request, один API-вызов по lease |
| `/internal/payments/reconcile` | `{"offset":0}` | Одна страница, до 5 транзакций; затем следующая offset вручную |
| тот же | `{"offset":0,"recover_archived":true}` | Явно восстановить подтверждённую привязку архивной charge для позднего операторского возврата, без повторного кредита |
| `/internal/payments/purge` | `{"dry_run":true}` | Предварительное количество архивов, без удаления |
| тот же | `{"dry_run":false}` | Только после проверки сроков/незавершённых дел и backup |
| `/internal/payments/retry-refund` | `{"charge_hash":"64 hex","acknowledgement":"CONFIRMED_NOT_REFUNDED_AFTER_TELEGRAM_RECONCILIATION"}` | Только после доказательства отсутствия возврата; открыть возможность одного нового запроса |

Получать charge из доказательства/status/сверки, а не из произвольного текста пользователя. Контакт поддержки не получает административные полномочия автоматически. Не помещать полные финансовые доказательства в публичные отчёты. Код не даёт пользовательской кнопки произвольного refund.

## Нормальный возврат и долг

1. Проверить окружение, владельца платежа, сумму, заказ и отсутствие уже завершённого возврата; сохранить номер обращения.
2. Вызвать refund-маршрут один раз. Он сначала сохраняет request и получает SQL lease, затем вызывает `refundStarPayment(user_id, telegram_payment_charge_id)`.
3. При подтверждённом `true` создать immutable refund notice; одной SQL-операцией провести settlement, уменьшение пыли, ledger и долг.
4. Проверить статус, `scripts/check_integrity_2_4.sql`, собственную историю пользователя. Не списывать дополнительно вручную.

Пример: куплено 100, израсходовано 75, доступно 25. Возврат снимает 25 (`refund:cash`), создаёт долг 75. Следующий GPT6 +5 отражается как +5 и −5 (`refund:repayment`), долг 70, баланс 0. Последующая покупка 270 даёт +270 и −70, доступно 200. Ни один старый расклад/прогноз не удаляется. Гонки с Таро −3 и прогнозом −4 сериализуются SQL; balance≥0 и SUM(ledger) сохраняются.

## Неопределённый исход и аварии

| Событие | Действие |
|---|---|
| successful_payment принят Telegram, D1 недоступна | webhook возвращает ошибку для повтора; затем восстановить по тому же update или getStarTransactions; не выдавать пыль ручным UPDATE |
| D1 credit прошёл, sendMessage упал | повтор webhook/история покажут тот же платёж, без нового кредита |
| API refund timeout/400/403/5xx/невалидный JSON | `needs_review`, **не повторять API вслепую**, сначала сверка и сервисный refunded_payment |
| API вернул true, но D1 compensation упала | request остаётся для разбора, наличные ещё не меняются; notice/reconciliation проведёт компенсацию один раз |
| 429 | `requested`, Retry-After сохраняется; повтор до срока не вызывает API; после срока оператор может повторить |
| Worker умер с `in_progress`, lease истекла | автоматического второго API нет; reconciliation, затем только явный retry после доказательства отсутствия refund |
| refunded_payment пришёл раньше успешной оплаты | сохранить возврат; поздний success не создаёт кредит и долг |
| forwarded invoice оплатил другой человек | нет кредита владельцу чужого заказа; аномалия сохраняется, подтверждённый возврат второму плательщику не снимает чужую пыль |
| charge уже архивирована | tombstone запрещает повторный credit; поздний реальный refund использует сохранённую сумму выданной пыли, может создать долг |
| fraction/nanostars, отрицательная сумма, неизвестный тип транзакции | не округлять и не кредитовать; invoice-транзакции с неподдерживаемой суммой сохраняются для ручной сверки |

Сверка обрабатывает только `type=user`, `transaction_type=invoice_payment`, целое положительное XTR и согласованный payload/owner; `source` — поступление, `receiver` — возврат. Неподдерживаемые направления не превращаются в покупку. Offset-пагинация не является постоянным надёжным checkpoint: при поступлении новых записей повторять перекрывающиеся страницы и полную сверку; дедупликация по charge защищает деньги. Сверка не назначена в Cron автоматически. Результаты каждой страницы и нерешённые дела проверяет оператор.

Для старой архивной charge без персонального receipt оператор сначала использует `recover_archived=true` с реальным доказательством Telegram; это создаёт проверенное дело, но не кредит. После личного удаления Telegram пользователя/утраты истории внешняя восстановимость не гарантирована: до коммерции нужен реальный протокол поддержки и backup.

## Хранение и удаление

/delete удаляет профиль, обычный ledger, прогнозы/Таро, активность и наградные claims; неоплаченные заказы тоже удаляются. Оплаченные orders/receipts, payer ID/charge ID и неразрешённые дела/долги сохраняются по публичным Terms. Повторная регистрация не обнуляет долг; новые положительные кредиты погашают его.

Очистка только вручную после dry-run. Группировать по плательщику: все заказы разрешены и выдержали свой retention, нет долга, свежих погашений и открытых аномалий/refund requests. Очистка группы проводится одной SQL-командой; личные доказательства и связанные settlements/repayments удаляются согласованно. Остаются charge hash, XTR/размер выданного пакета/scope/признак возврата и обезличенный audit, без payer ID. Это защита повтора платежа, а не тайная база людей. Хранение tombstone бессрочно раскрыто в интерфейсе; до включения торговли отдельно оценить правомерность и объём такой политики. Refund после purge проверен локально, включая создание долга после расходования.

## Обязательная внешняя приёмка до торговли

Прямой доступ к официальным Telegram pages вернул HTTP 403. При release-hardening независимо проверены публичные официальные исходники Telegram Bot API на закреплённом коммите; матрица полей/методов и границы проверки — ASTRA_2_4_OFFICIAL_CONTRACT_AUDIT.md. Это не проверка работающего endpoint. Владелец должен сверить https://core.telegram.org/bots/payments-stars, https://core.telegram.org/bots/api и https://core.telegram.org/bots/features; затем в dedicated test environment подтвердить endpoint, суммы/поля successful/refunded_payment и getStarTransactions, API true/ошибки/таймауты, доставку pre_checkout и service updates с текущими allowed_updates, 10-секундный срок, возврат после расходования и восстановление после сбоя. Проверить реальную D1 с триггерами/лимитами и CPU/1102. До этого Stars остаётся OFF; локальные тесты не дают разрешения принимать реальные деньги.


## Уточнения release-hardening

Непустой invoice start_parameter=stars ограничивает повторную оплату новых пересланных сообщений; ранее пересланные счета всё равно отклоняются по owner при pre_checkout. Несколько фактических charges чужого invoice остаются разными needs_review,каждый возвращается проверенному плательщику без дебета настоящего владельца заказа. amount у outgoing invoice transaction — положительная величина с receiver по официальному сериализатору; отрицательная или дробная сумма не округляется и сохраняется для разбора,включая amount0 с nanostar_amount.

Полный 64-символьный hash lookup использует индексируемый диапазон,поскольку Free D1 ограничивает LIKE/GLOB pattern50bytes. Purge сохраняет условия хранения,но ограничен 10 группами плательщиков и 10 закрытыми accounts за HTTP. Повторять dry-run/вызов до завершения; не считать одну страницу всей базой.

Оба сценария полной D1 outage проверены локально: success до SQL→503 и повтор даёт одинcredit; refundAPItrue→отказ всех SQL сохраняет in_progress lease,повторAPIне выполняется,а verified transaction page проводит компенсацию. Поздний webhook после cleanupjobs и удаления/регистрации не кредитует пакет заново. Локальный backup/restore сохранил proofs,ledger и owned texts; настоящий D1 rehearsal по RELEASE_CHECKLIST по-прежнему не выполнен.
