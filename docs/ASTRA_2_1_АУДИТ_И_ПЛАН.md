# Astra 2.1 — предварительный аудит и порядок безопасного внедрения

**Статус:** аналитические замечания на основании загруженного v2-архива. Это **не** готовое обновление рабочего бота. Пользователь сообщил, что продакшен запущен; внешние настройки Cloudflare здесь не проверены.

## Факты исходной v2

- Файлы: `01_ASTRA_V2.js`, `02_SCHEMA.sql`, `03_LOCAL_TEST.mjs`, `00_DIAGNOSTIC.js`, README.
- Схема: `astra_users`, `astra_processed_updates`. Binding в коде: `DB` → `astra-live-v2` (проверить фактическую привязку в Dashboard).
- Экономика сейчас: старт 2; дневной бонус +1; реферал +5; канал +5; 3 карты −3. Карта дня, гороскоп — бесплатно.
- В бесплатном гороскопе v2 **уже присутствует** `🔢 Число дня`. Расширенный гороскоп и новые цены — задача **2.3/2.4**, не 2.1.
- Локально выполнено `node --experimental-sqlite 03_LOCAL_TEST.mjs` на Node 22.16.0; результат: 30 assertions OK. Это не стресс-тест и не проверка реального Worker/D1.

## Конкретные находки в исходном коде

| Узел | Что видно в коде | Что исправить в 2.1 |
|---|---|---|
| `setZodiac` | `referral_rewarded=1` выставляется прежде `UPDATE` баланса реферера | Реферальный платёж + отметка — одно согласованное действие, безопасный повтор |
| `threeCards` | Баланс уменьшается до генерации/отправки; при явной ошибке отправки делается возврат | Сохранять заказ, список карт и статус; безопасное повторное получение без второй оплаты; обработать обрыв между шагами |
| `dispatch` | `astra_processed_updates` отмечает запрос до логики, при исключении запись удаляется | Однократные бизнес-операции и идемпотентность даже при повторных update и ошибках сети |
| `bonus`, `channelCheck` | Условные SQL-обновления защищают от части дублей, но нет журнала | Добавить ledger, согласованные обновления, сценарии параллельности |
| `/delete` | Удаляет только `astra_users` | Каскадно удалять/очищать пользовательские данные будущих таблиц; честная privacy-политика |
| `/activate` | `ASTRA_ADMIN_KEY` в query-параметре URL; `drop_pending_updates:true` | Убрать риск утечки секрета из URL и не сбрасывать очередь без необходимости |
| `broadcast` | Выбирает до 8 адресатов в минуту в заданном окне, помечает перед отправкой | Состояния доставки и безопасные повторы, оценить пропускную способность |
| Forecast | Готовые короткие фразы и `hash(sign+date) % 9 + 1` для числа дня | **Не менять в 2.1**; полное улучшение прогноза — этап 2.3 |

## Безопасный процесс владельца (без кода вручную)

1. **Сейчас**: загрузить `ASTRA_2_1_CODEX_PACK.zip` в локальный проект Codex/распаковать и дать задание из `01_CODEX_ЗАДАНИЕ_ASTRA_2_1.md`.
2. Codex делает аудит + локальные изменения + тесты и выдаёт релизные файлы. **Никакого Deploy.**
3. Перед реальной миграцией: по инструкции Codex сделать экспорт/бэкап базы `astra-live-v2` и сохранить исходный `01_ASTRA_V2.js`; зафиксировать число пользователей и суммарный баланс только агрегатами (без публикации Telegram ID).
4. Проверить миграции на тестовой D1, затем staging Worker и Telegram test bot, не подменяя основной webhook.
5. Только после просмотра результатов в ChatGPT — пошагово применить миграции в production и развернуть кандидат 2.1. Процедура отката обязательна.

**Секреты** (`ASTRA_BOT_TOKEN`, `ASTRA_WEBHOOK_SECRET`, `ASTRA_ADMIN_KEY`) не включать в ZIP, чат и Codex. Не исполнять SQL из Codex вслепую: он изменяет структуру продакшн-базы.
