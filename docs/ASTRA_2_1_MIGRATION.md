# Миграция 2.1: только после ревью, сначала staging

В этом задании всё выполнено только на локальном SQLite с фиктивными данными. Ни одна команда из этого документа не была выполнена на D1. Production Worker, DB binding, адрес, бот, webhook и Cron не менялись.

## Схема и атомарность

`migrations/0021_wallet.sql` — единственная миграция. Не изменяет исходные столбцы, не удаляет и не пересчитывает пользователей/processed_updates. Создаёт пять таблиц, индексы, пять триггеров и opening-записи. Старая схема: `src/02_SCHEMA.sql` (на существующей базе заново не нужна).

Новый профиль: 2 → ledger registration. Старый профиль: точный текущий баланс → ledger opening, один раз, даже если 0. Нет ретроактивного восстановления истории и повторной выдачи бонусов. Повтор файла безопасен при неизменённых определениях схемы. IF NOT EXISTS не обновляет уже установленные иные определения: если промежуточный кандидат уже ставили, нужна отдельная проверка версии/DDL.

Операции daily +1, channel +5, referral +5, tarot −3. Trigger guard проверяет наличие пользователя, баланс и eligibility; trigger post обновляет баланс/флаги и вставляет ledger. Referral trigger добавляет операцию из перехода zodiac NULL → значение; отказ ledger откатывает также выбор знака. Это стандартные SQLite statements/triggers, а не непроверенные JS-блокировки. Документация платформы для ручной сверки: https://developers.cloudflare.com/d1/sql-api/sql-statements/ и https://developers.cloudflare.com/d1/worker-api/d1-database/ . Совместимость этого конкретного DDL с D1 проверяется на staging; сетевого подтверждения документации в этой задаче нет.

## Перед миграцией

1. Сверить production с исходным снимком 2.0. Сохранить активную версию Worker/дату, схему и имеющиеся binding/настройки. Не публиковать секреты или данные пользователей в PR/чат.
2. Сделать экспорт/резервную копию D1 штатным способом Dashboard. Проверить восстановление копии в отдельной тестовой базе. Не считать непроверенный скачанный файл достаточным backup.
3. Записать агрегаты: `SELECT count(*) AS users, coalesce(sum(balance),0) AS total_balance FROM astra_users;` и `SELECT count(*) AS invalid FROM astra_users WHERE balance<0 OR typeof(balance)<>'integer';`. invalid должен быть 0. Отрицательный/дробный баланс — стоп, отдельное расследование.
4. Нужна полная остановка writers на время миграции: входящих webhook и Cron. Не сбрасывать webhook/очередь. Предлагаемый вариант для будущего согласованного окна — maintenance Worker из release: webhook отвечает 503, scheduled ничего не пишет. Дождаться завершения уже начатых запросов, перепроверить стабильность агрегатов. Учитывать ограниченное время повторов/хранения обновлений Telegram; длительная пауза может потерять события.
5. Сначала пройти весь процесс на отдельной staging DB с фиктивными данными. Нельзя мигрировать, пока v2 пишет: его referral/update balance не совместимы с новыми triggers.

## Точные будущие операции SQL

На staging новой пустой базе: сначала полный `src/02_SCHEMA.sql`, добавить только синтетические тестовые профили. На существующей production базе исходную схему/данные не заменять.

После остановки writers: выполнить полный `migrations/0021_wallet.sql` через SQL Console выбранной базы, сохранив журнал успеха. Затем по одному запросу из `scripts/check_integrity.sql`. Ожидаются нули для mismatches/unposted_operations/orphan_entries, пустой foreign_key_check, прежние число пользователей и сумма balance. Начальная сумма ledger равна исходной сумме balance. Запустить миграцию повторно на staging: количество opening/registration не увеличивается. Если ошибка посреди файла — writers оставить остановленными; найти причину, повторить только после ревью. Восстановление не требует DROP/очистки таблиц.

## Матрица staging для владельца/инженера

На новой отдельной D1 проверить DDL, trigger rollback, FK, тексты ошибок. Проверить параллельные webhook в разных Worker invocations: одинаковый update_id; новые update_id с одним message_id меню; разные меню при балансе 3; дневной и канал одновременно. Проверить два Cron, переход 23:59→00:00 Москвы, отказ Telegram 400/403/429/500, ответ после таймаута, остановку после фиксации операции и до доставки. Не использовать реальный production бот: только отдельный тестовый бот и тестовые аккаунты, управляемые владельцем вне этого задания. Отдельно проверить retry/backoff платформы и лимиты Free. После каждого сценария сверить scripts/check_integrity.sql и отсутствие второй оплаты. /delete и повторный /start проверить на primary, убедиться в отсутствии ссылок из других профилей.

## Откат и совместимость

До DDL: остановиться, оставить v2 без изменений. После DDL/до включения 2.1: не запускать оригинальный v2 с новыми триггерами — он может дважды начислить реферала и обойти ledger. Безопасный оперативный откат — `release/ASTRA_2_1_MAINTENANCE.js`: без записи в DB и без удаления новых данных. Сохранить снимок для расследования и подготовить исправленный 2.1 forward patch, затем повторить staging.

После начала работы 2.1 не восстанавливать слепо backup: это потеряет новые операции и может повторить платежи/бонусы. Обратной разрушительной миграции нет. Возврат к оригинальному v2 потребует отдельного согласованного плана сверки и изменения схемы, его сейчас не выполнять. Само наличие старых столбцов не означает безопасную совместную работу v2/v2.1.
