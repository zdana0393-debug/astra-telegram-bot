# TASK06 — решение consent28

10 ноября 2026, Москва. Разработана только согласованная 0028 и интеграция подписки. Финансы, выбор трактовок, кэши, paid snapshots и SQL0021–27 побайтно сохранены.

## Состояние и данные

Одна строка `astra_notification_consent28` на живой профиль: Telegram ID, generation, revision, версия `daily-forecast-v1`, серверный UTC epoch, `explicit_private_button`, update/message evidence, revoked_at. Pending: SHA-256 от 128-битного криптографически случайного nonce, привязки к версии/ревизии/сообщению и 900-секундное окно. Это отдельный random challenge, без HMAC-ключа бонусов. Имена, тексты личных сообщений, телефоны и pseudonym не сохраняются. Связанные данные персональны; proof/revoked и pending удаляются вместе с профилем при FK ON/OFF.

`astra_consent_runtime28` содержит только неперсональные schema/version/quarantine; первая установка quarantine1, никакого backfill. `astra_delivery_consent28` привязывает одну попытку outbox к замороженной ревизии согласия. Эта маленькая отдельная таблица нужна для preflight, поскольку менять колонки0027 нельзя. Удаляется при удалении профиля или outbox; не служит архивом ID. Индексы ограничивают выбор active/pending.

Открытие страницы создаёт pending, отправляет статический текст и связывает nonce с **реальным message_id результата Bot API**. При неясном результате отправки/DB-bind кнопка не пригодна для grant. Приватный callback сверяет actor/chat, ID, message, hash, TTL, revision/version/current generation. Одним UPDATE+триггером записывает proof, потребляет nonce и включает настройку. Ошибка любого триггера откатывает всё. Имеющийся update_jobs со статусом working подтверждает происхождение update; processed_updates обеспечивает обычный replay. Статическое опубликованное уведомление версионируется в исходниках.

/stop и явный OFF — атомарный D1 batch с отзывом/очисткой pending и OFF. SQL-триггер также отзывает право при любом совместимом UPDATE notifications_enabled=0. Ревизия увеличивается, незавершённые sending/retry старой ревизии отменяются. Старый grant/cancel/toggle не может вернуть право; новое согласие требует нового экрана. Повтор /stop не продлевает момент первого отзыва. /delete удаляет запись триггером в той же транзакции, что профиль; неудачное удаление не оставляет частичное стирание.

## Три SQL gate

1. Candidate SELECT JOIN users+user_policy+consent: живой профиль, совпавшее поколение, ON, поддерживаемая версия, consent_at, отсутствие revoked_at.
2. Атомарный INSERT/UPSERT claim повторяет предикат; дополнительные 0028 BEFORE guards проверяют готовый runtime и quarantine0. AFTER capture сохраняет ревизию/версию для этой попытки.
3. Непосредственно перед **каждым** HTTP SQL JOIN проверяет token/sending, delivery-map/frozen revision, текущее право, generation/sign, ON, lease/cooldown, runtime/version/quarantine. После read нет промежуточного await перед запуском транспорта. Из SQL также читается текущий owned для единственной CTA. Старые paid/free тела возвращаются без перегенерации.

Внешний Telegram не участвует в транзакции D1. Отзыв, завершённый до preflight, блокирует отправку; уже начатый HTTP не отменить, микроскопическое межсистемное окно после read неизбежно. Exactly-once не обещается. Unknown — terminal без слепого retry, отправка остаётся доступна вручную.

## Совместимость очереди и бюджет

Протокол TASK03 сохраняется: общий lease90s, московская дата, реальное окно06:00–07:59UTC, cooldown по полному retry_after, attempts≤3, terminal protection, legacy markers, bounded cleanup, 403 блокирует/отзывает, 429 с частичной доставкой unknown. D1 отказ при фиксации принятого HTTP оставляет unknown/sending, которое позже становится unknown, без дубля. Если сама D1 недоступна после403/429, гарантированно записать отзыв/cooldown невозможно — операторский риск, не скрываемый локальными тестами.

Партия4 вместо8; счётчик считает **каждый SQL statement**, включая batch, и каждый HTTP. Guard46 внутренних операций оставляет резерв2 внешних для HMAC purge/base schema; lease release зарезервирован до начала новой работы. Перед cache load резервируются до3SQL, перед claim —1claim,2операции на каждую часть (preflight+HTTP),1finalize и1дополнительная операция429/403. Если места нет, подготовленный cache сохраняется, claim не создаётся, следующий invocation продолжает. Отказы учитываются до выполнения; дополнительная безопасная фиксация unknown также попадает в guard. Максимум не заменяет реальный Cloudflare CPU/rows.

## Fail-closed schema и включение

Два D1 чтения проверяют полные name/type/DDL0028 и runtime completion. Финансовый manifest126 не расширяется нефинансовыми таблицами; отдельный consent manifest проверяет новую схему. Console completion дополнительно сверяет definitions до migration_done1. Неполная/чужая схема не открывает UI-grant или доставку; базовые ручные функции остаются доступны при прежней готовой схеме.

Доставка требует env `ASTRA_DAILY_DELIVERY_ENABLED=true` **и** quarantine0, а затем всё равно персональное право. По умолчанию OFF/quarantine1; никаких дат/включений не назначается. Health всегда public_ready=false/ready=false для кандидата; schema/manual/delivery blockers показаны отдельно. Runtime-gate заменяет абсолютный исторический TASK05 STOP-SHIP только технически; публичный STOP-SHIP до реальной приёмки остаётся.

После восстановления старой БД факт позднего /stop или /delete сам не обнаружится. До restore envOFF, writers остановлены, восстановленная копия quarantine1; затем сверка поздних событий либо отдельный прозрачный повторный opt-in. При отсутствии доказательств доставка остаётся закрытой. Это не скрытый вечный реестр и не автоматический сброс настроек старых пользователей.
