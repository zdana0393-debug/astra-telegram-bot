# Astra 2.5 TASK05 — разрешение блокеров TASK04

11 ноября 2026. Только локальные синтетические данные. Это дополнение к неизменённым отчётам TASK04. **STOP-SHIP сохраняется.** Успешное воспроизведение прежней ошибки не считается приёмкой нового кандидата.

## B1: историческая ссылка на удалённого реферера

Исходная схема `src/02_SCHEMA.sql` допускает отсутствующего родителя. Оригинальный `/delete` его не воссоздаёт. Неизменённый SQL 0025 отвергает такую запись при включённых FK. Владелец отдельно разрешил минимальную нормализацию перед 0025 в задании TASK05.

Добавлен явно именованный шаг `migrations/compat/astra25-before-0025-referrers.v1.sql`. Это не миграция 0030 и не новая версия финансовой политики. Единственный UPDATE устанавливает `referrer_id=NULL`, только если соответствующего профиля действительно нет. Нет INSERT, DDL, создания пользователей, изменения `referral_rewarded`, `channel_rewarded`, балансов или финансовых проводок. Корректные ссылки сохраняются.

Новый manifest `data/astra25-upgrade-plan-task05.json` включает SHA шага, исходные SQL и новый TASK05 Worker. Порядок: 0021 → 0022 → 0023 → 0024 → **compat v1** → 0025 → 0026 → 0027 → 0028 → 0029. Старый manifest и SQL 0021–0029 неизменны.

Runner `scripts/astra25-upgrade-task05-local.mjs` работает только с новой локальной копией. До исправления он проверяет точную исходную схему, делает native backup, отдельно восстанавливает копию и сверяет fingerprints. Журнал `.task05/journal.json` содержит агрегатное число затронутых связей и hash ожидаемых пользователей до первого UPDATE. Публичные результаты не перечисляют удалённые ID. Приватный backup содержит исходные данные и требует обычного ограничения доступа/срока хранения; это не новый реестр идентификаторов.

Preservation не ослаблена до «игнорировать astra_users»: для каждого исходного столбца и rowid вычисляется точная ожидаемая проекция, разрешающая только эту замену ссылки. Все остальные таблицы, rowid, sqlite_sequence и содержимое остаются под прежними hash-проверками. Даже когда compat ничего не меняет, DDL совпадает с 0024: завершение определяется журналом и expected-stage, а не одним fingerprint схемы. При неопределённом состоянии — STOP, без force/resume наугад.

Принятые исходные состояния — только точные схемы 2.0–0024 с такой проблемой. Orphan на 0025+ не получает нового автоматического разрешения. Чужая/частичная схема, self-referral, неверные финансовые типы, wallet mismatch и активированные политики по-прежнему запрещены.

### Награды и повторная регистрация

У выплаченного исторического приглашения сохраняется `referral_rewarded=1`; у pending — исходный 0. После обнуления отсутствующего родителя договор с ним не создаётся. Повторная регистрация прежнего ID не восстанавливает удалённую связь и не переназначает старого приглашённого через `/start ref_...`. Уже выплаченная награда не выдаётся повторно. Корректный pending-referral действующего родителя продолжает оплачивать существующую legacy-награду ровно один раз. Это проверено реальным новым Worker и неизменными финансовыми триггерами.

Существующая политика HMAC после `/delete`, финансовых остатков и сроков хранения не менялась. Совместимость не обещает восстановить материалы, которые оригинальная 2.0 никогда не сохраняла в D1.

## B2: каскад status/error screens

Новые `src/tarot25/ui05.mjs`, `runtime05.mjs`, `scripts/build-2.5-task05.mjs` собирают **отдельный** `release/ASTRA_2_5_TASK05_CANDIDATE.js`. Старые UI/runtime/build и TASK03 candidate сохранены.

- Принятый Telegram текст и неудачный `editMessageReplyMarkup` рассматриваются отдельно. Ошибка клавиатуры оставляет успешный ACK текста действительным, регистрирует короткое техническое событие и не открывает новый error screen. Вернуться можно через обычное меню Таро и историю.
- Неудачный status body отмечается как уже выполненная попытка UI. Внешний обработчик не вызывает ещё один такой экран. У покупки один общий error reporter вместо двух вложенных.
- Material HTTP сохраняет прежний ранний порог 42; остальной Tarot HTTP получает порог 45 на invocation-local счётчике для резерва завершения. Это не глобальная квота Cloudflare. Конечный бюджет дополнительно проверяется внешней диагностикой SQL и fake HTTP, включая завершение update.
- SQL оплаты, lease/finalize, sealed snapshot, цены, авторизация, generation и 96-битные HMAC callback не изменены. Неизвестный исход не вызывает автоматическую повторную отправку. Явное ручное чтение предлагает предупреждение о возможном дубле, не списывает пыль и читает сохранённый результат, максимум три части на страницу.

Прежний тест на TASK03 по-прежнему воспроизводит 33 SQL + 16 HTTP = 49 и HTTP500. Новый тест на TASK05 с HMAC/архивом58000/markup400 получает **34 SQL + 13 HTTP = 47**, HTTP200. Проверены также cutover-clock, markup400/403/429/500, body400/403/429/500/network/timeout/ACK без message_id, частичная доставка, временные ошибки D1 до/после покупки и finalize, повторные callbacks, stale/чужие/подменённые подписи и удаление. Точная итоговая матрица находится в `data/astra25-task05-verification.json`.

## Что этим не решено

Реальные Workers CPU/1102, D1 транзакции/квоты/rows и Telegram transport не измерялись. Обрыв ACK остаётся неопределённым: нельзя обеспечить одновременно отсутствие потерь и отсутствие повторного сообщения во внешнем API без подтверждения. Финансовое списание при этом сохраняет идемпотентность.

Неоплаченные draft сохраняются бессрочно при живом профиле: 10 000 реальных локальных предложений уже превышают 500 МБ. Retention и rate policy требуют решения владельца и отдельного согласованного forward-only изменения. Очистка в TASK05 не реализована. Публичные продажи/Stars/бонусы/доставка остаются OFF; публичный запуск не принят.

## Дополнительная находка QA: mutation могла ничего не менять

Старый `tests/tarot25-ui.test.mjs` заменял первый hex-символ offer_id на фиксированный f. Для UUID с исходным f получалась исходная подписанная кнопка и законная покупка вместо проверки подделки. Повтор полного прогона выявил этот случай. Исправлена только эта строка теста: f→e, остальные→f, плюс assert неравенства payload. MAC/финансовый код не ослаблялись. Новый TASK05 тест делает такую же гарантированную подмену и проверяет отказ. `test-astra25-task05-history.sh` запускает прежние suites с этим исправлением; exact-diff guard допускает только данную строку, все остальные исторические исходники остаются под freeze. Прямой старый TASK04 driver ожидает прежний тест и не используется вместо нового TASK05 driver.

Уточнение размера: исторический тест с именем58000 строил57000 UTF16 units; его исходник и результат49 сохранены. Новая fixture гарантирует assert длины58000; все32 затронутых UI-теста повторены после уточнения, включая полное чтение пяти страниц. Итоговая матрица machine report использует именно дополнительный прогон58000.
