# Astra 2.2: архитектура и границы изменений

Основа — ветка astra-2.1-hardening, коммит a3a02f2. В удалённой astra-2.2-shell уже находилось ТЗ 02_CODEX_ЗАДАНИЕ_ASTRA_2_2.md; оно сохранено. Изучены актуальный Worker, миграция 2.1, контрольные SQL, аудит, план миграции, тесты, паспорт Astra 3.0 v0.2 (включая разделы 1–3, 12–13, 16–18) и применимые правила справочника MASTER. Спецификация 3.0 описывает будущие функции, не текущее состояние.

## Существующий фундамент

В 2.1 один ES-module Worker: fetch → секрет webhook → schemaReady → dispatch с working/done и арендой → incoming/callback. Планировщик отдельно вызывает broadcast. D1-binding остаётся DB. Нет npm или платного runtime API.

Финансы живут в astra_operations и SQLite triggers: guarded INSERT фиксирует баланс, ledger, флаги и текст расклада одним statement. Для старых пользователей есть opening balance; для новых — registration 2. Повтор меню закреплён в astra_tarot_requests. Повтор webhook и lease отправки защищают от обычных конкурентных дублей. Исходные CHECK разрешают только daily/channel/referral/tarot. Менять их ради новой оболочки не требуется.

## Изменения 2.2

Сохранён отдельный release/ASTRA_2_1_WORKER.js; release/ASTRA_2_2_WORKER.js произведён из него с точечными изменениями. forecast, dayMSK, dayCard, threeCards, операции bonus/channel, dispatch и broadcast сохранены; оболочка добавляет MAIN_SECTIONS, screen, shellPage, FAQ и secretArchive. В incoming добавлены шесть новых разделов и код; старые названия и callback_data продолжают работать. У callback добавлены shell:* маршруты, неизвестные пункты отвечают спокойным экраном с выходом. Бизнес-функции не зависят от истории навигации.

Одна отправка — один короткий экран, plain text, без parse_mode и editMessageText. Так повтор редактирования не влияет на финансовые операции и ключи меню. Самые длинные статические страницы, кнопки, все ветки навигации и FAQ покрыты обходом в тестах. Никакой UI не просит дополнительные личные данные.

Новый путь трёх карт: предложение → подтверждение → прежний threeCards. Callback подтверждения несёт номер исходного сообщения-предложения, а не номер каждого вновь отправленного подтверждения. Поэтому повторы экрана не создают разные покупки. Старое tarot:three остаётся прямым исполнением прежнего предложения с уже указанной ценой. Последний сохранённый результат просматривается бесплатно и не меняет баланс или статус старой доставки.

Награда хранится отдельно в astra_shell_rewards, PRIMARY KEY(telegram_id,code), code ограничен gpt6. INSERT ... ON CONFLICT DO NOTHING выполняет атомарный AFTER trigger: +5 к balance и ledger с reason=easter:gpt6, operation_id=NULL. При отказе ledger весь statement откатывается. astra_operations не получает фиктивных channel/referral и его CHECK не меняется. Дополнительный astra_shell_erase очищает награду после удаления профиля независимо от PRAGMA foreign_keys; прежний astra_erase остаётся без изменений.

schemaReady 2.2 требует все 8 таблиц и 8 триггеров (в том числе три новых). Неполная миграция даёт /health 503, webhook 503 и неисполнение Cron. Проверка имён — защита от пропущенной установки, не доказательство корректности произвольно изменённого DDL. Контроль схемы на staging остаётся необходимым.

BOT_USERNAME принимается как безопасное имя 5–32 ASCII-символа без @, с буквой в начале. Валидное env.BOT_USERNAME используется в реферальной ссылке; невалидное/пустое значение возвращает исходный fallback, как требует ТЗ. Поэтому на тестовом Worker переменная обязательна по инструкции, иначе ссылка поведёт к исходному боту.

## Риски, оставшиеся от 2.1

SQLite не равен распределённому D1. Локальные тесты не подтверждают staging, реальные лимиты Free или доставку Telegram. После неопределённой отправки повтор сохранённого текста может дать дубликат без нового списания; Cron консервативно допускает пропуск. Долгая приостановка Worker сверх lease может продублировать внешний send. /delete не отзывает уже начатую отправку и не удаляет сообщения Telegram/резервные копии. После удаления и новой регистрации архивная награда снова доступна: антифрод-след тайно не сохраняется.

Изменения предназначены только для тестового Worker astra-staging-21-worker и DB astra-staging-21. Ни deploy, remote SQL, live Telegram API, webhook, Cron settings, ни секреты в этой задаче не менялись.
