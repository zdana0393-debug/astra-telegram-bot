# TASK07 — один контролируемый переход2.0 →2.5

**Черновик будущей процедуры, не разрешение выполнить её сейчас.** Основной бот/действующая D1/сломанная staging не использовались. В TASK07 выполняются только локальные действия на фиктивных данных. Все реальные export/import/Time Travel/переключения ниже требуют отдельного решения владельца. Публичный STOP-SHIP остаётся.

## Что подготовлено

Владельцу не нужно устанавливать промежуточные Workers2.1/2.2/2.3/2.4. Локальная программа на новой копии применяет настоящие SQL-файлы в порядке:

`2.0 →0021 →0022 →0023 →0024 →compat-referrers.v1 →0025 →0026 →0027 →0028 →0029 →0030 →0031`.

Manifest `data/astra25-upgrade-plan-task07.json` фиксирует SHA каждого файла, полные DDL286 объектов и SHA matching `release/ASTRA_2_5_TASK07_CANDIDATE.js`. Нельзя подставлять старый Worker или произвольный dump. Compatibility v1 только очищает ссылки на отсутствующих рефереров до0025, не выдаёт наград и не меняет paid/pending признаки. Эта ограниченная проекция отдельно показывается до обновления. Другие несовместимости — STOP.

Нативный runner читает source только read-only, делает backup и **отдельную восстановленную копию**, сравнивает данные, rowid/sequence и FK/integrity до SQL. Каждый migration-файл выполняется в локальном BEGIN IMMEDIATE целиком. Журнал prepared-before-COMMIT позволяет отличить rollback от неизвестного успешного COMMIT. Изменённый target, живой lock, чужая/неполная схема, wallet mismatch, несогласованные paid/ledger или исходник с активными gates останавливают работу. Ни skip-check, ни force, ни понижение FK для обхода не предусмотрены.

## 1. Инвентаризация и read-only preflight

До окна обслуживания владелец с инженером отдельно фиксируют: какой Worker/его SHA действительно работает; точные таблицы/триггеры/версии D1; существующие bindings, webhook endpoint/allowed_updates, Cron и gates; ожидающие Telegram updates/платежи/возвраты; число профилей, каждый баланс, сумму, ledger, paid hashes, update_id, поколения и consent. Секреты не копировать в чат/отчёт. Не считать название «2.0» достаточным: проверяется фактическая схема.

Если Cloudflare отдаёт SQL export, инженер сначала восстанавливает доверенный файл в **новую частную локальную SQLite**, затем сверяет его с read-only инвентаризацией исходной D1. Нельзя просто переименовать .sql в .sqlite. Обычный SQL dump может не сохранять скрытые rowid: для таблиц, где они существенны для истории/курсоров, нужны явный export rowid и отдельная сверка; без lossless доказательства — STOP. Локальный runner гарантирует сохранность относительно проверенного локального source, а не автоматически относительно неизвестного облачного dump. Служебные D1-объекты и фактическая исходная схема требуют отдельной приёмки; не удалять их наугад ради прохождения preflight.

Рабочая2.0 не сохраняла paid-тексты в D1. Отсутствующий старый результат нельзя восстановить миграцией. Существующие сохранённые материалы более новых исторических состояний сохраняются побайтно; не выдумывать отсутствующую историю и opening entries не выдавать за прежние транзакции.

Будущий локальный preflight выполняется на **частной, согласованной, проверенной копии**, а не на live DB:

```sh
node --experimental-sqlite scripts/astra25-prepare07-local.mjs \
  --local-only --source /private/origin.sqlite \
  --output /private/new-target.sqlite --preflight
```

`READY_FOR_LOCAL_REHEARSAL_ONLY` означает только, что локальный исходник распознан. `NOT_READY_STOP` с кодом причины — остановиться, сохранить отчёт и исследовать; не править балансы/схему вручную. Чужие триггеры, изменённые миграции, неизвестные права или порванные refs в современном состоянии не исправляются автоматически. На стадии0024 и после compat DDL одинаковы: runner безопасно повторяет идемпотентную совместимость при этой неразличимости, не угадывая, что она уже применялась.

## 2. Окно обслуживания, остановка writers и проверяемый backup

Заранее сообщить пользователям о паузе. В отдельной согласованной операции остановить **все** старые writers: HTTP/webhook обработку, Cron/очереди, административные скрипты, платежные reconcile/refund jobs. Это включает старые версии Worker и любые другие записи в ту же базу. Обычный параметр `--writers-paused` — подтверждение оператора, он физически ничего в Cloudflare не выключает. Пока нельзя доказать отсутствие writers — STOP.

Владелец выбирает способ удержать входящие Telegram updates без потерь и обрабатывает неприменённые события после cutover. Временная ошибка webhook может вызвать повтор Telegram; длительность хранения updates ограничена Telegram, бесконечного буфера нет. Не использовать `drop_pending_updates=true` для удобства. Реальные платежные/возвратные события фиксировать в защищённом журнале сверки, без повторного начисления.

После остановки получить согласованный export/backup, записать время/bookmark, SHA, размер и защищённое место хранения. **Восстановить отдельно** и сверить все таблицы/типы/rowid/sequence, каждый баланс, ledger и paid hashes. Time Travel Free —7 дней, не обещанные Paid30; одной фразы «backup есть» недостаточно. Для давно существующей alpha D1 может требоваться иной backup-механизм: выяснить subsystem по официальной инструкции. Ни backup, ни restore здесь не выполнялись на реальном Cloudflare.

Рабочую старую базу пока не мигрировать. Частную копию реальных профилей не подключать к функциональному тестовому боту. Это разные задачи: проверка переноса данных и испытание Telegram на синтетических профилях.

## 3. Подготовка итогового пакета одной локальной командой

Node22.16+ с native SQLite; проверен Node24.22.1. Все выходные пути новые, абсолютные, без URI/symlink/hardlink. SQL package и компактная копия должны находиться **вне Git**. Каталог владелец заранее создаёт0700.

```sh
node --experimental-sqlite scripts/astra25-prepare07-local.mjs \
  --local-only --source /private/origin.sqlite \
  --output /private/new-target.sqlite --writers-paused \
  --compact-output /private/new-compact.sqlite \
  --sql-output /private/new-import.sql
```

Программа применяет21…31 на новой копии, оставляя source прежним. `.task07` содержит backup, отдельный restore и журнал с SHA; не удалять его до завершения приёмки. После прерывания миграции повторить **тот же** source/output с `--resume`, без указания уже существующего compact-output; затем подготовить новую компактную копию отдельной CLI-командой: `node --experimental-sqlite scripts/astra25-compact07-local.mjs --local-only --writers-paused --source /private/new-target.sqlite --output /private/recovery-compact.sqlite --sql-output /private/recovery-import.sql`. Все выходы должны быть новыми. Программа никогда не перезаписывает существующий target/SQL package. Если неясно, был ли COMMIT, не подставлять новый source/manifest и не удалять lock наугад.

Компактное восстановление создаёт таблицы, затем буквально исходные данные с rowid и sqlite_sequence, затем триггеры/индексы/представления. Это предотвращает повторное исполнение финансовых post-триггеров во время загрузки уже существующего ledger. FK остаются ON и deferred до COMMIT; после — полный foreign_key_check, integrity, DDL и независимые типизированные fingerprints. Нет пересчёта/повторного начисления денег. Большие TEXT/BLOB разбиты на bounded SQL chunks; staging-таблица импорта удаляется до установки исходных триггеров. Она не является финансовой таблицей. SQL использует `unhex` для сборки больших ячеек; его поддержку настоящей D1 обязательно проверить отдельно.

В локальном stock-тесте10000 старых unpaid+1 paid после21…31 и bounded очистки файл оставался664072192 байта; **DELETE не уменьшил файл**. Проверенный логический restore дал4870144 байта, с теми же балансами/ledger/paid bytes/rowid/sequence. Это доказательство локальной компактной копии, не D1 quota/reclaim. Данные реального пользователя не разрешено очищать по примеру этого теста: retention/gates/операционные права требуют отдельного решения. Избыточный файл>500MB нельзя просто импортировать в D1 Free; сначала локальная сверка и разрешённая процедура компактного переноса.

## 4. Будущая приёмка на совершенно новой D1

Только после нового разрешения создать **новую изолированную** D1, убедиться, что она пуста и её ID не совпадает ни с production, ни со сломанной staging. Для функционального Telegram использовать пакет с синтетическими профилями. Реальную копию данных проверять отдельно без доставки сообщений.

Выбрать **один** путь: импорт подготовленного итогового SQL package либо отдельная облачная репетиция исходной копии со всей цепочкой миграций. Не импортировать готовую0031 и затем повторно накатывать21…31. Новая схема уже содержит весь релиз. Нет ручной установки промежуточных Workers.

Cloudflare D1 CLI/import не равен локальному SQLite transaction: сначала на синтетическом клоне доказать поведение всего файла, отложенных FK, больших cells/unhex, всех триггеров, table-valued PRAGMA page_count/page_size и прерванного импорта. `0031` содержит133 административных statements, каждый≤20429 байт; это **не** Worker invocation с50 запросами. В local compact package21578 statements для stock fixture, каждый≤28398 байт. Не вставлять огромные SQL-строки вручную в Console и не уменьшать проверки ради лимита50. Официальный import выполняется файлом; согласованный инструмент/атомарность должны быть подтверждены до переноса реальных данных. Не включать `BEGIN/COMMIT` в D1 import-файл: оператор создаёт там внешние транзакционные границы по документации платформы. Наш SQL package их не содержит.

После загрузки повторить независимую сверку: все пользователи/балансы/ledger/оплаченные3/5/RWS/forecast, raw bytes, Telegram processed/pending updates, поколения, notification consent и request receipts. Сверять типы/Unicode/NUL/BLOB и rowid/sequence, не только количество строк. Любое несоответствие — STOP и новая копия из проверенного backup. Никаких произвольных «исправляющих UPDATE» финансов.

Затем отдельный matching Worker TASK07 и binding **только к новой базе**. Env flags false: `ASTRA_TAROT25_ENABLED`, `ASTRA_TAROT25_STORAGE_TEST_MODE`, `ASTRA_TAROT25_INDEPENDENT_TEST_MODE`, `ASTRA_TAROT25_QUESTIONS_TEST_MODE`, `ASTRA_ECONOMY_V2_ENABLED`, `STARS_SHOP_ENABLED`, `ASTRA_DAILY_DELIVERY_ENABLED`. SQL29.enabled=0, SQL30.write/cleanup=0, SQL31.enabled/questions/cleanup=0; старые policy/patch enabled/activated0, consent delivery_quarantined1. Дату новой редакции не устанавливать. Cron/webhook не менять автоматически.

`/health` TASK07 намеренно возвращает503, `public_ready:false`, `ready:false`, `release_scope:TASK07_LOCAL_CANDIDATE`. Проверить `tarot25_schema_ready:true`, `tarot25_sales_enabled:false`. Не подделывать общий ready=true ради зелёного экрана. Сначала платформенные измерения/ручной тест, затем отдельное решение о выпуске и статусе readiness.

## 5. Переключение и восстановление

Сначала владелец принимает финансовую сверку, реальные CPU/1102/D1 metrics, синтетический Telegram test environment, новый UX/privacy/цены/сроки и резервное восстановление. Только после этого — отдельное управляемое переключение к новой паре Worker+DB с writer fence и reconciliation отложенных updates/платежей/возвратов/удалений/consent. Zero downtime не доказан и не обещается.

До cutover исходная база неизменна. При сбое подготовки не затрагивать её, остановить новую копию и повторить из проверенного backup. После cutover в новой базе уже могут быть новые покупки: обычный возврат к2.0/2.4/TASK06 приведёт к пропускам ledger/consent/семантики0031. **Старый Worker не является обычным rollback.** Сначала остановить новые writers, сохранить новое состояние и список поздних событий. Предпочтителен matching forward-fix. Если нужен restore — отдельное доказанное восстановление с повторной сверкой и идемпотентным применением событий после bookmark; не терять /delete и отзывы согласия. Вручную «отыгрывать» балансы или перегенерировать paid запрещено.

Финансовые флаги, рассылка, Stars и cleanup остаются OFF до каждого отдельного утверждения. Следующий этап — согласованная платформенная приёмка; TASK08 этим документом не начинается.
