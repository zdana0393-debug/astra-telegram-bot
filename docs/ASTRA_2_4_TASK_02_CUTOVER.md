# TASK 02 — условия будущего включения компактной редакции

9 ноября 2026. Инструкция подготовлена для владельца; никаких действий в Cloudflare/Telegram не выполнено. Это не установка всего релиза и не TASK 03/05.

## Что поставлено

Единый `release/ASTRA_2_4_WORKER.js` пересобирается командой `node scripts/build-2.4.mjs`, содержит TASK 01 и TASK 02. Маркер кандидата — `ASTRA-2.4-task02`. Новая редакция: engine_version `forecast-1.0.0+compact.1`, content_version `2026.11-compact-v1`; исходная selection/seed-версия **по-прежнему `forecast-1.0.0`**, исходный каталог `2026.11-v1`, число `legacy-hash-v1`.

Миграции для TASK 02 **не нужны**. Не менять таблицы, миграции 0021–0026, денежные флаги, бонусы, HMAC или магазин ради форматирования. Не менять расписание, webhook и opt-in пользователей. До установки общего релиза действуют отдельные ограничения и runbook TASK 01.

## Настройка только по будущему решению

1. Сначала принять редакционные образцы и источник каждого тезиса, завершить разрешённые этапы и проверку единой установки. Ничего не включать автоматически по факту коммита.
2. Владелец выбирает **будущую московскую дату** D. В Cloudflare Dashboard для будущего staging Worker предусмотрена обычная переменная `ASTRA_FORECAST_COMPACT_START_DAY` со значением этой даты в формате `YYYY-MM-DD`. Не копировать сам placeholder и не назначать прошедшую дату для получения превью. Конкретная дата этим коммитом не выбрана и не установлена.
3. Существующая `ASTRA_FORECAST_START_DAY` остаётся прежней: это граница включения самого движка 2.3B, а не новой редакции. Не заменять её новой переменной. Оба денежных feature flags остаются OFF до отдельного решения.
4. Пока новая переменная отсутствует/пуста — генерация новых записей остаётся в прежней редакции. До D — также прежняя. При D и позже **на cache miss** применяется компактный формат. Бот получает дату прежним способом Europe/Moscow; время машины разработчика не участвует.
5. Уже сохранённый sign/day/ru имеет абсолютный приоритет даже после D: старые `free_text`, `extended_text`, `source_tags` и версии читаются как есть. Уже оплаченный пользовательский `result_text` открывается дословно, бесплатно. Новая дата не меняет прежние покупки, знак покупки или число.
6. Если D ошибочно задана несуществующей датой, uncached-генерация завершается ошибкой без вставки или списания; кэш продолжает читаться. Текущий /health не является валидатором этой новой переменной: проверить дату явно перед будущим включением. Исправление конфигурации не должно сопровождаться удалением кэша.

На тестовом наборе будущего staging проверить знак до/на границе D, совпадение числа с прежней версией, одну новую запись, повторный free read и одну покупку расширенного за 4. Повторить чтение при отключённой новой переменной: созданный кэш должен остаться прежним, а не перегенерироваться. Покупка и повтор работают по существующим SQL-инвариантам; права на бонусы не зависят от форматтера.

Движок 2.3B уже хранит результаты глобально. Поэтому нельзя «показать новую редакцию» для старой даты посредством UPDATE/DELETE кэша. Прошлые даты в `ASTRA_2_4_TASK_02_SAMPLES.md` — локальное редакционное превью чистой функции, отдельно обозначенное в отчёте. Не воспроизводить его перезаписью D1.

## Ручное чтение и будущая рассылка

`formatFreeForecast` формирует один документ; результат сохраняется в `free_text`. Ручное чтение и существующий scheduled-потребитель уже используют тот же `getForecastDaily`/`sendFreeForecast`. В TASK 02 не менялись часы, число получателей, очереди, opt-in, доставки, кнопки и учёт активности. Новая редакция сама по себе не исправляет ранее заявленную проблему рассылки — это отдельный TASK 03 после команды владельца.

## Проверки и возврат к прежнему отображению

Исходные engine/catalog/service/UI 2.3B сохранены побайтно. Тест удаляет из нового Worker добавленный редакционный модуль, возвращает маркер и единственное переключение генератора: SHA восстановленного файла совпадает с TASK 01. Это контроль отсутствия посторонних изменений, **не инструкция устанавливать старые Workers поверх новой схемы**.

При проблеме выключить только переменную новой редакции для ещё не созданных записей и выпустить совместимое исправление. Созданные компактные записи и оплаченные результаты всё равно остаются неизменными. Нельзя очищать их для «отката». После 0026 по-прежнему запрещён обычный откат к старым несовместимым Workers; применяется runbook TASK 01 с writer pause и исправлением вперёд.

Перед реальным включением нужны staging-замеры cold/warm CPU и ошибок 1102, D1 rows_read/rows_written и размера базы. Новый код не добавляет запросов D1, однако справочник, валидация и более подробный trace увеличивают размер Worker и сохранённой записи. Локальные Node wall_ms и SQLite не доказывают Cloudflare Workers Free 10 мс/50 запросов/500 МБ. Реальные Telegram/D1 в текущем задании не использовались.
