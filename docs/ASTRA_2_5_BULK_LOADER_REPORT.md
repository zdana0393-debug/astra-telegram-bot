# Windows-загрузчик колоды: локальная реализация

13 ноября2026, Москва. Реализован исполняемый GUI, не макет. Исходная ветка `astra-2.5-tarot`, база `d85c093`. Настоящий пилот принят по сообщению владельца; его приватный pilot.json остаётся на Windows, не копировался в Git.

## Что готово

- `tools/tarot-bulk-loader/START_WINDOWS.cmd` запускает графическое окно: выбор manifest/двух ZIP/pilot.json, скрытый токен, личный ID, установка Pillow кнопкой, локальная подготовка, прогресс156, остановка/продолжение и разбор неизвестного исхода без редактирования JSON.
- Используется прежний строгий импортёр оптимизированных JPEG и180° версий. Входные PNG не нужны. Принятый кэш не перерабатывает78 карт при каждом запуске. SHA отправляемого файла проверяется непосредственно перед HTTP.
- getMe/getChat проверяют существующего бота и подтверждённый положительный private chat_id. Окончательное окно запрашивает разрешение на конкретный оставшийся объём. Успешный pilot.json при совпадении bot/chat/SHA/art_version засчитывает прямого Шута:155 новых фото вместо156.
- Фото идут последовательно с интервалом≥2сек;429 сохраняет retry_after+запас. Три429 приостанавливают проход. Нет getUpdates, изменений webhook, платежей или D1.
- Состояние атомарно сохраняется до отправки и после каждого ACK. ОС-lock исключает два процесса и снимается системой после аварии. Прежнее sending становится unknown; автоматического повторения нет. GUI разрешает дополнительную отправку только после явного разбора владельцем с предупреждением о возможном дубле; история попыток остаётся.
- Полный приватный `telegram-registry.json` появляется после156 корректных уникальных file_id и совместим с существующим `validateTelegramArt`/приватным сборщиком Worker. Бот, пользователь, источник и ориентации зафиксированы; менять получателя существующего журнала нельзя. Результаты находятся в `%LOCALAPPDATA%\Astra25DeckLoader`, вне Git; токен туда не записывается.

Полный результат принят реальным JS-валидатором и приватным сборщиком; single-file проходит `node --check`.

34 регрессионных теста пилота подтверждают совместимость общего Telegram-клиента. Общий клиент изменён только для безопасного чтения retry_after и правильного имени файла каждой карты; старый пилот остаётся двухсообщенческим и без повторов.2 теста новой read-only диагностики выполнены в native SQLite с query_only=ON и доказали отсутствие изменений строк. Всего59 выполнений, ошибок0. Импорт/синтаксис GUI проверены; настоящий Windows GUI и настоящая массовая отправка ещё не выполнялись. Нельзя выдавать fake ACK за реальные156 file_id.

## Минимальная подготовка переноса данных

`scripts/production25-readonly-inventory.sql` содержит6 SELECT-запросов: фактическая схема и столбцы, количество пользователей/общий баланс/невалидные значения/реферальные аномалии/даты, настройки уведомлений и обработанные update_id. Нет индивидуальных профилей или секретов. На production не запускалось. Запросы агрегатов объединены, чтобы уменьшить повторные сканирования.

Для последующего локального backup/restore и миграции уже существует `scripts/astra25-upgrade-task07-local.mjs` и библиотека upgrade07: source открывается read-only, создаются проверенный backup и отдельный restore-proof, миграции21…31 применяются только к новой копии, сверяются типы/rowid/balances/paid/ledger, есть resume и контроль чужих writers. Этот механизм не переписывался и не заменялся более слабым. Реальная схема/экспорт D1 ещё не получены; служебные D1-объекты и совместимость платформы должны проверяться на фактическом источнике после разрешения.

Настоящие CPU/SQL capabilities/import/restore/D1 limits и вывод /health ещё требуют реальной приёмки. Константа ready не менялась для обхода STOP-SHIP. Переключение рабочего бота сейчас не разрешено и не выполнено. После подтверждённого реестра можно сразу собрать приватный Worker прежним сборщиком; JSON вручную редактировать не нужно.
