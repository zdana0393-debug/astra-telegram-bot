# TASK 03 — будущая проверка и включение ежедневного Cron

9 ноября 2026. Это инструкция для владельца после общего ревью релиза, а не выполненные настройки. Codex не открывал реальную D1, не устанавливал Worker, не создавал Cron Trigger и не вызывал настоящий Telegram. TASK 04/05 ещё не выполнены.

## Что известно и что предстоит установить

По прежнему коду рассылка уже существовала: только **06:00–07:59 UTC = 09:00–10:59 Москвы**, до восьми адресатов за запуск, лишь с `notifications_enabled=1`, выбранным знаком и без журнала доставки на эту дату. Восемь — не предел аудитории. Один Cron раз в сутки обслуживал бы лишь первую партию; повторные запуски нужны для остальных. Прежний 429 попадал в терминальный журнал, а прежняя очистка требовала попадания ровно в 06:00 UTC. Это реальные ограничения кода; они **не устанавливают причину** недоставки работающего бота. Настоящие Trigger, окружение, привязки D1, Telegram-ошибки и прежние настройки согласия без Dashboard неизвестны.

Новая очередь использует прежний сохранённый `free_text`. Формат TASK 02B применяется лишь при уже согласованной владельцем дате `ASTRA_FORECAST_COMPACT_START_DAY`; патч не устанавливает её. Старый кэш не переписывается. Без даты приходят прежние полные 2.3B-тексты, с тем же бесплатным числом дня. Ранее оплаченные результаты открываются без списания.

## До единой будущей установки

1. Дождаться отдельного решения владельца об установке полного кандидата. Выбрать **тестовый Worker и тестовую D1**, проверить названия/ID в Dashboard самостоятельно, не отправляя ключи в чат. Не работать с основным ботом.
2. Повторить резервное восстановление в отдельной тестовой базе по [release checklist](ASTRA_2_4_RELEASE_CHECKLIST.md) и [руководству 2.4](ASTRA_2_4_STAGING_GUIDE.md). Убедиться, что сохранены балансы, ledger, покупки и paid snapshots. Копия файла SQL без проверенного восстановления недостаточна.
3. На время записи SQL остановить все writers **по отдельному разрешению владельца**: старые Cron, webhook-обработку и фоновые операции. Не использовать случайно старый Worker после новых финансовых миграций.
4. Если основа — 2.3B, по существующим инструкциям выполнить **0024 → 0025 → 0026**, не перескакивая проверки каждого этапа. Если эти миграции уже применены, сначала установить фактическое состояние; не пересоздавать базу. TASK 03 не меняет ни одного финансового SQL-файла.
5. Добавить **нефинансовую 0027**. Cloudflare Dashboard → Storage & databases → D1 → выбранная staging-база → Console. Вставлять каждый файл целиком, последовательно: `migrations/0027_steps/01_queue.sql`, затем `02_delivery_guards.sql`, затем `03_cleanup.sql`. Это точная конкатенация `migrations/0027_broadcast.sql`. Не разбивать триггеры по точкам с запятой. Последний шаг устанавливает `migration_done=1`.
6. Проверить [read-only integrity SQL](../scripts/check_integrity_broadcast03.sql): нет missing objects, mismatch, orphan, invalid attempts, missing sent marker и foreign key errors; runtime singleton существует и `migration_done=1`. Новых объектов — **11**, прежний базовый manifest — **126**. Если шаг оборвался, writers остаются остановленными, исправляется причина и повторяется соответствующий целый шаг; `IF NOT EXISTS` не чинит чужое повреждённое определение триггера — его сравнивает владелец с файлом.
7. Установить будущим решением только новый `release/ASTRA_2_4_WORKER.js` вместе с этой схемой. **Оба финансовых feature flags остаются OFF**, дата компактной редакции не добавляется автоматически. Привязку `DB`, token и существующую `ASTRA_FORECAST_START_DAY` проверить без смены webhook/секретов в рамках TASK 03. После 0025 нельзя выполнять обычный откат к старому финансовому Worker. После 0027 старый broadcast тоже блокируется guard-триггером: безопасный путь — совместимое исправление вперёд либо согласованное полное восстановление проверенного backup без writers.

## Проверка Dashboard и согласия

1. Workers & Pages → нужный Worker → **Settings → Bindings**: `DB` указывает именно на ожидаемую staging-D1. Название пункта может быть «Bindings» на отдельной вкладке. Не публиковать значения secrets.
2. Открыть `/health` тестового Worker. Проверить базовые `schema_ready`, `forecast_ready`, `ready` и добавленные поля: `broadcast_schema_ready`, `broadcast_ready`, `broadcast_blocker`, `broadcast_window_utc`, `broadcast_window_open`, `broadcast_batch_limit`, `broadcast_cooldown_until`. `broadcast_window_open=false` вне утра нормально. `broadcast_ready=true` означает готовность кода/схемы, **не наличие Trigger и не доказательство доставки**. Общий `ready=false` может относиться к неизменённой конфигурации бонусов; не включать новые бонусы ради зелёного статуса — читать конкретные blocker-поля. Ошибка конфигурации compact даты должна быть исправлена владельцем, а не заменена произвольной датой.
3. В тестовом боте выбрать знак и **самостоятельно включить уведомления** существующим переключателем; проверить ON на экране. Новые регистрации теперь создаются с OFF. Миграция не включает подписки массово и не меняет прежние OFF/ON. В старой схеме DEFAULT был 1: наличие старого ON само по себе не доказывает добровольное согласие. До рассылки прежней аудитории владелец должен подтвердить основания её подписки; при отсутствии подтверждения решение об отдельном явном opt-in принимается прозрачно, без фиктивного согласия и скрытого SQL-переключения всех пользователей.
4. Проверить OFF на втором тестовом аккаунте: сообщение не приходит, ручное «Открыть бесплатно» возвращает полный тот же прогноз. `/stop` отключает будущие отправки; уже начатый запрос Telegram нельзя отозвать. После `/delete` обычные очереди удаляются; новая регистрация OFF. HMAC-права, удаление и retention TASK 01 не меняются.

## Где включить Trigger после будущего общего деплоя

Только по отдельному решению владельца: Workers & Pages → **нужный Worker → Settings → Triggers → Cron Triggers → Add**. В некоторых версиях Dashboard раздел называется **Trigger Events**. Проверить список существующих triggers до добавления; не оставлять лишние расписания от старой версии.

Рекомендуемое выражение для утреннего окна:

```cron
* 6-7 * * *
```

Один запуск каждую минуту с 06:00 до 07:59 **UTC**, то есть 09:00–10:59 Москвы; Cron Cloudflare задаётся в UTC, отдельного Moscow timezone у выражения нет. Расписание один раз в 06:00 недостаточно для аудитории больше одной партии. За окно максимум 120 событий; пустой запуск не отправляет сообщений. Изменение Trigger распространяется не мгновенно — закладывать до 15 минут и сверять фактические timestamps. Не нажимать публичное «Run now» ночью в ожидании отправки: код проверяет **фактическое время**, а не старый `scheduledTime`.

В этом задании выражение только подготовлено; ни один реальный Trigger не добавлен и не изменён.

## Проверка очереди, ошибок и пропусков

Workers & Pages → Worker → **Observability / Logs** и **Metrics**. По будущему разрешению включить необходимые логи, учитывая retention и стоимость. `ASTRA_D1_DIAGNOSTICS=true` включает уже существующую агрегированную диагностику; после замера владелец решает, оставлять ли её. Не публиковать токены, Telegram ID, тексты пользователей, SQL bind-параметры или внутренние support-данные.

Искать JSON-события `astra_broadcast03` с reason, candidates, claimed, sent, retry, blocked, unknown, failed, cancelled, d1_calls, statements, http. Событие `astra_d1_invocation` показывает весь invocation, включая прежние две внешние D1-операции. Дополнительно выполнить вручную только в выбранной базе [read-only диагностику](../scripts/diagnose_broadcast03.sql), по одной полной SELECT-команде. Она содержит агрегаты, не тела сообщений и не ID. Внутренние lease/token не предназначены для публичного сообщения.

| Наблюдение | Проверка/значение |
|---|---|
| Нет Cron events | Проверить нужный Worker, расписание UTC, сохранение Trigger и время распространения. Код не может создать Trigger сам. |
| `outside_window` / `forecast_not_active` | Фактическое время либо дата активации 2.3B не допускает отправку. Никаких ночных догоняющих сообщений. |
| `broadcast_schema_unavailable` | Проверить все 3 шага 0027, 11 объектов и финальную отметку; ручное меню сохраняется при готовой базовой схеме. |
| `no_due_recipients` | Проверить ON, знак, policy generation, сегодняшние sent/unknown/legacy jobs и last_broadcast_day. Не удалять журнал для насильственной повторной отправки. |
| `budget_yield` | Нормальная передача остатка следующему запуску; уже подготовленный кэш сохраняется. |
| `busy_or_cooldown` | Другой запуск владеет lease (90 секунд) либо ожидается retry_after. Проверить время, затем дальнейший прогресс. |
| `telegram_cooldown` | 429, весь бот ждёт не меньше retry_after. До принятой части допускается не больше 3 попыток за дату, затем failed. |
| blocked / 403 | Telegram отказал: подписка того же поколения профиля выключена атомарно. Поддержка проверяет собственные защищённые журналы; повторное включение — только пользователем после устранения причины. |
| unknown / sending, потерянный ответ | Автоматически не переотправлять. Зависший sending после истечения lease становится unknown. Telegram мог принять сообщение; ручной прогноз доступен. |
| `forecast_unavailable` | Проверить конфигурацию редакции, кэш, D1 и версии. Ложный delivery claim до подготовки текста не создаётся. |
| `storage_or_budget_failure` / `storage_finalize_unavailable` | Проверить D1/лимиты/состояние схемы. Не стирать claim. После доступности D1 lease освобождается или истекает, sending становится unknown. |

Старые legacy sent/sending/unknown/rejected намеренно не переигрываются: прежний Telegram-исход уже неизвестен. Полный прогноз доступен вручную. Обновление успешно, когда конечная тестовая аудитория 8/20/100 полностью проходит следующие ограниченные вызовы без дубликатов; не когда один вызов обработал 100 адресатов. При длительном 429, недоступной D1 или неопределённом Telegram-исходе гарантировать доставку всем невозможно. Новые свежие адресаты выбираются перед разрешёнными повторами; конечная очередь проходит без потери более низкого нового ID.

## Обязательные staging-замеры и восстановление

Для **8, 20, 100 искусственных opt-in подписчиков**, разных знаков, проверить cold отсутствующий кэш, warm кэш, повтор одного Cron, параллельные Trigger, ON/OFF, оплату и повторное чтение старого результата. Не делать 100 отправок в одном invocation. В тестовом сценарии без ошибок 100 обслуживаются несколькими запусками; сравнить sent count с исходным количеством. Реальную массовую тестовую аудиторию создаёт владелец отдельным планом, без рассылки случайным пользователям.

Проверить в Cloudflare фактические **CPU (10 ms Free)**, ошибки 1102, D1 subrequests (50), а также HTTP subrequests, `rows_read`, `rows_written`, объём одной D1 (500 MB), суточные квоты и рост кэша/журнала. Новый локальный guard считает даже отдельные statements внутри batch плюс Telegram HTTP и резервирует две внешние операции; SQL-триггеры не бесплатны по rows/CPU. В существующей диагностике `first()` может не иметь meta: `rows_complete=false` означает неполное наблюдение, **не нулевые расходы**. Использовать D1 Metrics/Analytics и реальные query meta там, где они доступны; не подменять их числом SQLite-запросов или Node wall time. Увеличение cleanup/rows-потребления оценивать и на старом большом журнале.

В отдельном локальном fault injection уже проверены 403/429/timeout, отказ D1 до отправки и при финализации, неизвестный исход после принятия, отключение между частями и повторный Cron. Эти ошибки не следует провоцировать на основном боте. На staging отдельно подтвердить собственные инфраструктурные отказы/восстановление безопасным согласованным способом.

Если release smoke не прошёл: остановить отправки и writers согласованным способом; сохранить журналы и backup; определить, были ли реальные новые финансовые операции. Не откатывать только Worker/таблицу ledger. Исправлять совместимой новой сборкой либо восстанавливать согласованный полный снимок после сверки финансов и внешних Telegram-платежей; повторное применение миграции не воспроизводит потерянные операции. После восстановления повторить integrity, balance=SUM(ledger), paid read и smoke. Во время TASK 03 никакие из этих внешних действий не выполнялись.
