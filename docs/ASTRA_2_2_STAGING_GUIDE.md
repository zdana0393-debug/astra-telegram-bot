# Astra 2.2: ручная установка только на тестового бота

**Цель:** Worker astra-staging-21-worker, D1 astra-staging-21, binding DB. Не выбирать production Worker opel-astra-bot, DB astra-live-v2 или рабочую Astra 2.0. Эта инструкция подготовлена для владельца после ревью; Codex ничего не деплоил и не вызывал Telegram API.

## Подготовка и пауза

1. Проверить Draft PR/сравнение astra-2.2-shell → astra-2.1-hardening, аудит архитектуры и тестовый отчёт. Не объединять main автоматически.
2. Открыть Cloudflare Dashboard → Workers & Pages → **astra-staging-21-worker**. Проверить название до любого изменения. В Settings → Bindings сверить DB → **astra-staging-21**. Если привязка другая — остановиться и исправлять только тестовый Worker отдельным решением.
3. Сохранить текущий JS тестового Worker 2.1, version/deployment и настройки. Сделать резервную копию тестовой D1 и проверить её восстановимость. Не экспортировать production и не передавать реальные данные/секреты в чат.
4. В Settings → Variables and Secrets добавить/проверить обычную **Text variable BOT_USERNAME**: фактическое имя тестового бота без @. Не вставлять сюда токен. У тестового Worker должны остаться его собственные уже настроенные ASTRA_BOT_TOKEN, ASTRA_WEBHOOK_SECRET, ASTRA_ADMIN_KEY и при необходимости CHANNEL_USERNAME. Значения никто не просит присылать. При пустом/невалидном BOT_USERNAME fallback ведёт к исходному боту, поэтому вручную проверить реферальную ссылку особенно важно.
5. На время SQL поставить только тестовый Worker в паузу: например, согласованно заменить его код на сохранённый release/ASTRA_2_1_MAINTENANCE.js (503, без DB-записей и Cron). Дождаться завершения старых запросов. Webhook и Cron settings не менять; не удалять pending updates. Длительную паузу не держать: Telegram не хранит очередь бесконечно.

## SQL через Dashboard D1 Console

6. Открыть Storage & databases → D1 → **astra-staging-21** → Console. Убедиться, что установлена полная схема 2.1 из migrations/0021_wallet.sql. Этот релиз предназначен поверх 2.1, не поверх чистой 2.0. Если база ещё пуста/схема неполная — остановиться и сначала отдельно подготовить тестовую 2.1 по её инструкции; не применять 0022 к случайной базе.
7. Сохранить агрегаты до установки: `SELECT count(*) AS users, coalesce(sum(balance),0) AS total_balance FROM astra_users;`. Выполнить запросы scripts/check_integrity.sql; расхождений быть не должно.
8. Для Console использовать **по одному целому файлу** в таком порядке:
   - migrations/0022_steps/01_rewards.sql — таблица награды;
   - migrations/0022_steps/02_guard.sql — проверка существования профиля;
   - migrations/0022_steps/03_post.sql — атомарные +5 и ledger;
   - migrations/0022_steps/04_erase.sql — удаление награды при /delete даже с FK OFF.

Каждый файл копировать целиком, включая BEGIN…END одного CREATE TRIGGER, и нажимать Execute отдельно. Не разрезать trigger по внутренним точкам с запятой. Файл migrations/0022_shell.sql — точная конкатенация тех же четырёх шагов для инструментов, принимающих весь SQL; **не требуется выполнять оба варианта**. Если Console выдаёт «No SQL statements detected», оставить writers на паузе, проверить, что вставлен весь отдельный SQL-оператор без Markdown-ограждений; не объединять остальные триггеры и не ослаблять ограничения.

9. Все шаги IF NOT EXISTS повторяемы при одинаковых определениях. Ошибка посреди установки — причина оставить паузу, исправить после ревью и повторить нужные шаги. Нельзя вручную выдавать пыль UPDATE balance, менять CHECK, удалять таблицы или ledger.
10. После установки повторить scripts/check_integrity.sql и выполнить по одному запросы scripts/check_integrity_2_2.sql. Ожидаются нули для всех расхождений, пустой foreign_key_check и прежние users/total_balance. Сама миграция **не начисляет** награду всем пользователям. На этой стадии rewards пусты, если коды ещё не вводили.

## Один JS-файл

11. Workers & Pages → **astra-staging-21-worker** → Edit code: заменить всё содержимое JS на **release/ASTRA_2_2_WORKER.js**. Это самостоятельный ES module без npm/импортов/сборки. Не добавлять его под старым файлом. Только владелец выполняет Deploy тестового Worker после проверки имён и привязки.
12. В Deployments сверить активную версию. Открыть `/health` именно тестового Worker: version ASTRA-2.2.0-candidate, schema_ready=true, ready=true. Без 0022 /health и webhook намеренно дают 503. Значения секретов health не раскрывает.
13. **Не вызывать /activate и не выполнять setWebhook.** Существующий тестовый webhook /telegram-webhook и его секрет остаются. Если webhook тестового бота ещё не настроен, его отдельная настройка не входит в эту инструкцию/задачу: нужна отдельная контролируемая процедура владельца исключительно для тестового бота. Не менять webhook рабочего бота. Cron settings остаются прежними; на staging проверяется только уже разрешённое тестовое расписание.

## Проверка с телефона на тестовом боте

14. /start: новичку 2 ✨, выбор 12 знаков; существующий знак и баланс не сбрасываются. После выбора знака — бесплатный прежний прогноз с числом дня. Главное меню — 6 кнопок, два в строке.
15. Пройти все шесть разделов и «Назад»/«Главное меню». Об Астре → манифест, доверие (гороскоп/Таро/пыль/будущее), команда, 11 вопросов FAQ и подробные ответы, правила и privacy. Проверить читаемость на реальном телефоне: такая визуальная проверка локальными тестами не подтверждается.
16. Досье сверить с реальными тестовыми знаком/балансом/настройкой. Включить/выключить рассылку; /stop выключает её. /help, /privacy, /delete работают. Будущие портрет/совместимость/натальная карта/архив/Stars честно в подготовке, оплаты нет.
17. Бонус дня +1 один раз на московскую дату, карта дня повторяется бесплатно. Реферальная ссылка содержит **имя тестового бота**, реферал нового профиля +5 только после первого выбора знака; повтор выбора не начисляет. Канал проверять только если тестовый бот имеет нужные права в выбранном тестовом канале, без изменения production.
18. Таро: цена 3 ✨ видна до подтверждения, простой переход к подтверждению не списывает. Повтор подтверждения одного предложения не списывает второй раз; «Последний расклад» возвращает сохранённый текст бесплатно. Старая inline-кнопка 2.1 также работает. После сбоев не выдавать деньги вручную — проверить сохранённую операцию.
19. Для проверки пасхалки на тестовом профиле ввести `gpt6`, затем ` GPT6 `. Только первый ввод +5; SQL показывает одну astra_shell_rewards и одну ledger-запись easter:gpt6 с operation_id=NULL. На другом тестовом профиле награда своя. /delete → /start действительно новый профиль: награда вновь доступна, старые данные удалены.
20. Повторить оба контрольных SQL-файла. Политики D1, лимиты Free, реальные повторы Telegram и Cron проверить на staging отдельно; SQLite не доказывает их корректность.

## Откат только тестового Worker

При ошибках — вернуть maintenance JS, сохранить тестовую БД для расследования, не удалять новые данные. При полном корректном 0022 можно вернуть сохранённый **release 2.1** тестового Worker: прежние таблицы/CHECK/erase не заменены, новый erase trigger продолжит удалять награды, ledger учитывает уже выданные +5. Проверить это контролем SQL; интерфейс пасхалки при таком откате просто исчезнет. Не возвращать старый src/01_ASTRA_V2.js (2.0) поверх ledger-схемы. Не восстанавливать старый backup поверх новых операций без отдельной сверки. Частичная/изменённая схема — оставаться в maintenance и делать forward fix. Production эта процедура не касается.
