# Astra 2.4A: тестовый отчёт и границы приёмки

7 ноября 2026, Europe/Moscow. Ветка **astra-2.4-economy**, база **astra-2.3b-forecast-engine**, hardening **2d73738**, подготовительное задание **9b79a97**. Оба обязательных документа прочитаны полностью. Node.js **24.22.1** (требование 22+), встроенный node:sqlite, фиктивный fetch Telegram, синтетические профили. Cloudflare/Telegram/реальная D1 не вызывались.

## Реализовано

- Полная доступная история из существующего astra_wallet_ledger, по **12 записей**: московская дата/время, конкретная причина, точное изменение пыли, текущий баланс. Opening подписан как исторический снимок; registration — начальный баланс при регистрации. Известны все 8 действующих причин; неизвестная причина не пропускается, показывается нейтрально без сырого ключа. Отдельных ledger id не выдумывается.
- Кнопки истории в пыли и досье, обновление, листание Старее/Новее, Назад/Главное меню. Курсоры состоят из направления и двух base36 rowid-локаторов, не содержат Telegram ID/исходных ключей/charge ID. Каждый boundary/snapshot проверяется по владельцу; запросы связаны с authenticated from.id. SQL с bind-параметрами, без OFFSET, LIMIT 13. Snapshot rowid отсеивает вставки между страницами, включая задние даты и одинаковые timestamp. Порядок — created_at/idempotency_key; при одинаковой секунде ключ задаёт устойчивый технический порядок, не доказанную микросекундную последовательность операций.
- `astra_activity_days`: одна московская дата на профиль, только осмысленные личные действия после выбора знака. Учитываются известные команды/меню/callbacks. Не считаются Cron, автоматическая доставка, группы, неизвестный текст/кнопки, health, payment/service events, повторы update и старые pending jobs. Выбор знака учитывается после сохранения, даже при ошибке отправки ответа. /delete не создаёт активность.
- Точная текущая серия/общее число дат, календарные пропуски, 3/7/30 как наблюдательные этапы без наград. Если последняя дата вчера — серия сохраняется до окончания сегодняшнего дня; если раньше вчера — 0. Новый визит после пропуска начинает серию с 1. Нет ретроактивных дат, новых начислений или штрафа за пропуск.
- Экономическое досье, фактические правила пыли, дополнение /privacy. Дополнительный guard/erase обеспечивают удаление и отсутствие orphan activity при FK OFF и откате JS на 2.3B.

### 31 новый сценарий

- 500 смешанных записей плюс начальная запись, 42 страницы, одинаковые timestamp и точный порядок, без дублей/пропусков; обратное листание возвращает ту же страницу.
- Новая верхняя/задняя/совпадающая по времени строка во время просмотра не попадает в зафиксированные страницы; обновление показывает все новые записи.
- Чужой snapshot/anchor, SQL-подстановка, слишком большой/невалидный курсор, неизвестные причины, пустая история, opening/registration, положительные/нулевые/отрицательные суммы.
- EXPLAIN использует **idx_astra_ledger_history**, без TEMP B-TREE/OFFSET. Telegram plain text, callback ≤64 UTF-8, ограниченные UTF-16 chunks, точное восстановление суррогатных пар.
- 0024 до/после сохраняет все старые SQL-объекты, балансы и ledger; повторяемость и точное совпадение split/combined. Каждый отсутствующий новый объект — health/webhook 503, Cron не пишет.
- 90 последовательных дат через 29 февраля; 90 реальных dispatch-вызовов через Новый год; 31.12→01.01/московская полночь, пропуск/восстановление, этапы 3/7/30 без денег.
- Новый профиль до знака не активен; сохранение знака с ошибкой Telegram учитывается; успешные/ошибочные повторы после полуночи и прежние pending jobs не добавляют дат.
- **20 конкурентных callbacks** одной даты и отдельно **20 независимых SQLite-соединений**: одна activity row, прежний ledger/баланс. 20 последовательных действий — одна попытка INSERT, без UPDATE активности. При конкурентной гонке попыток INSERT может быть несколько, но добавляется ровно одна строка.
- Сбой INSERT активности и отдельный сбой добавочного SELECT прежнего job не блокируют оплату/снимок расширения и не дублирует списание. Новое успешное действие может зафиксировать текущую дату, старые даты не выдумываются.
- FK ON/OFF и /delete через **прежний 2.3B**: удалены только данные владельца, чужие даты/балансы сохранены; повторная регистрация не возвращает старую активность. Read-only integrity и foreign_key_check после удаления — без нарушений.
- Равенство тел финансовых/forecast функций; сохранённые старые Таро/прогнозы при новой схеме; /privacy, отключённый магазин, отсутствие вызовов invoice/pre-checkout/refund.

Прежняя денежная регрессия также включает 20 callbacks/SQLite connections для покупок, rollback ledger, Telegram 400/403/429/500/сеть/невалидный JSON, смену знака/версии после покупки и длинные архивы. Локальный SQLite не доказывает поведение реальной D1.

## CPU/D1 и стоимость — оценка с явными границами

`ASTRA_2_4A_METRICS.json` создан локальным `scripts/economy-review.mjs`. Размер single-file: **525 271 → 539 192 bytes** (+2.65%). Холодный parse/evaluate в Node VM (20 контекстов): median **1.258 → 1.215 ms**. История, две query и форматирование, 100 тёплых вызовов: median **0.078 ms**, p95 **0.169 ms**. Форматтеры времени лениво переиспользуются, не создаются заново на каждую строку.

Первая локальная операция активности заняла **13.025 ms wall-clock**, повторная — **0.111 ms**. Холодная инициализация Intl/Node может быть существенной. Эти замеры **не CPU Cloudflare**, не startup isolate, не HTTP/Cron/Telegram/D1 latency, и не доказательство лимита Workers Free 10 ms либо отсутствия 1102.

| Чистая новая операция | SQLite statements | Попытки записи | Изменённые строки |
|---|---:|---:|---:|
| Первое сохранение активности | 2 | 1 | 1 |
| Повтор той же даты | 1 | 0 | 0 |
| Первая страница истории | 2 | 0 | 0 |
| Следующая страница | 2 | 0 | 0 |
| Сводка активности | 1 | 0 | 0 |

Это **не** D1 rows_read/rows_written. Для нового осмысленного update добавлен ещё SELECT прежнего job (защита от ретраев); регистрация знака может потребовать повторной проверки eligibility после сохранения. Уже завершённый повтор отсекается до этих действий. Cron/health не вызывают трекер. Guard/PK добавляют индексные чтения/записи при INSERT. Новый индекс истории увеличивает размер и стоимость каждого будущего ledger INSERT, хотя деньги и триггеры прежние; само создание индекса сканирует имеющийся ledger.

Снимок/anchor читаются индексированно, page fetch возвращает до 13 записей, без глубокого OFFSET. При множестве новых вставок после snapshot движок может отфильтровать больше кандидатов: SQL LIMIT не гарантирует ровно 13 rows_read. COUNT дат читает историю владельца; recursive chain — текущую серию через PK. Поэтому большая аудитория с длинными сериями может приблизиться к дневным лимитам по чтению даже при одной roundtrip на сводку.

Хранение: максимум **одна новая строка на активного человека/московскую дату**; ориентир 44–45 bytes только полей (8-byte ID, ISO day, UTC created_at, source), **без** SQLite row headers/PK/B-tree/backup. 10 000 ежедневных активных профилей дают 3,65 млн строк/год, от ~161–164 MB сырых полей, фактический размер выше. Не введены скрытые очистки или retention оплаченных данных.

Указанные в прежнем review квоты (Workers Free 10 ms CPU; D1 5M rows_read/day, 100K rows_written/day, 5 GB) требуют проверки актуального тарифа владельцем. В этой задаче официальные API/реальные сервисы не вызывались. До увеличения аудитории измерить cold/warm CPU, 1102 и D1 metadata/счётчики на staging, включая COUNT длинной серии и старые финансовые записи с новым индексом. Нельзя объявить эксплуатацию неограниченно бесплатной по node:sqlite.

## Известные ограничения и безопасное продолжение

1. **Активность — отдельная статистика с приоритетом сохранения основных функций.** Ошибка D1 при её записи логируется без персональных данных и не блокирует платный материал. При таком отказе дата может быть пропущена; из ретраев/рассылок она не достраивается. Это осознанная граница, проверенная fault-тестом. Для более строгого восстановления нужна отдельно согласованная долговечная очередь, а не ручное подправление дат.
2. История доступна в пределах реально существующего ledger; opening не реконструирует старые операции. Равные UTC-секунды упорядочены ключом. Курсоры не рассчитаны на VACUUM/перезапись/удаление ledger во время просмотра; после таких действий открыть историю заново. Сам Worker этого не делает.
3. Дедупликационные jobs/processed_updates и их прежний 14-дневный retention сохранены. Не заявляется вечная защита от произвольного повторного проигрывания очень старых payload вне окна Telegram/старого механизма. Exactly-once внешней доставки нет.
4. Реальная D1, Telegram, телефон и CPU/квоты не проверялись. Факт работающей staging 2.3B — сообщение владельца, не самостоятельный запрос Codex. Production/основной бот не трогались.

**Владельцу:** принять review и экранные примеры; перед 2.4A дополнительно сохранить подтверждение ledger/CPU/D1 для уже работающей 2.3B, backup/restore rehearsal, сверить имена staging. Затем по отдельному решению выполнить четыре шага Console, сравнить агрегаты/три integrity-скрипта, установить один JS и провести smoke/метрики по **ASTRA_2_4A_STAGING_GUIDE.md**. При ошибке — maintenance и rollback JS на 2.3B без удаления SQL/снимков. Ничего из этого Codex не выполнял. Merge в main не делался. 2.4B и Stars — только будущий отдельный этап.
