## Точный порядок и отдельные разрешения

**A — создание инфраструктуры, разрешение запрашивается после этих документов.** Владелец подтверждает аккаунт, имена и лимиты. Можно создать две новые пустые D1 и два новых Worker с блокирующей заглушкой503, без bindings, secrets, Cron и GitHub auto-deploy. Создание Worker в Dashboard включает начальную публикацию заглушки — это тоже deploy и входит только в явное A. Пример полного кода заглушки: `export default {fetch(){return new Response('TASK08: admission pending',{status:503});}}`. Другого кода A не разрешает. Сохранить выданные ID/URL и скриншоты выбранного аккаунта в закрытом журнале.

**B — отдельное подтверждение после реестра ID и подготовки кода.** Проверить, что все целевые IDs — ровно вновь созданные ресурсы. Затем предъявить владельцу конфигурации, SQL-пакеты и SHA диагностического harness/локального relay. Только после B: remote SQL исключительно на новых D1, deploy reviewed harness и существующего кандидата, отдельные тестовые secrets, Telegram test API/реальные тестовые сообщения, временное включение RWS/questions/GC только внутри закрытых испытаний. Разрешение A не разрешает B. У неизвестного harness сейчас нет одобренного SHA — его нельзя деплоить по одному описанию.

**C — завершение теста.** Вернуть тестовые gates OFF, остановить relay; удаление тестовых ресурсов или изменение тестового webhook — по отдельному согласованному действию. Production никогда не входит в A/B/C. Переход рабочего бота требует другого разрешения после итогов TASK08.

## Отдельный Telegram test bot и получатели

После B владелец входит в dedicated test environment Telegram и создаёт **нового** бота через BotFather в том окружении. Это не существующий основной бот и не его token. Порядок входа зависит от официального клиента; коды входа/2FA сюда не отправлять. Сверить актуальную официальную документацию перед действием. Проверить `test/getMe` только с новым token; если test realm не подтверждён — STOP, не fallback на обычный API.

Выдуманные числовые IDs из SQLite не являются адресатами настоящего Telegram. Для настоящих сообщений нужны отдельные назначенные Telegram IDs владельческих test-realm аккаунтов. Их не берут из production. Профили/знаки/вопросы полностью вымышлены, собственные имена/телефоны/здоровье/третьи лица не вводятся. Список разрешённых test IDs хранится частно; в публичный отчёт — только количество/псевдонимыA/B.

Предпочтительный первый транспорт — **локальный allowlist relay**: `test/getUpdates` только нового бота → фильтр разрешённых test IDs → POST test-candidate `/telegram-webhook` с новым секретным заголовком. Кандидат получает настоящий формат updates и отправляет ответы в test API; посторонние updates не пересылаются и не архивируются. Relay ещё не реализован/не одобрен. Несуществующей env-переменной allowlist у кандидата не придумывать. До reviewed relay или другой доказанной изоляции получателей тестовые RWS-флаги не включать.

Это не проверка зарегистрированного Telegram webhook: такой case остаётся NOT_TESTED. План по умолчанию **вообще не вызывает setWebhook/deleteWebhook**, не меняет даже test webhook. Если владелец захочет прямой test webhook, отдельно согласовать его URL, recipient gate, allowed_updates и код; production token/URL исключены. Для relay достаточно message/callback_query. Платёжные updates не инициируются, invoices/Stars/refunds API не вызываются. При ошибке не делать `drop_pending_updates=true`.

После получения разрешённых test-realm IDs подготовить новый dataset с ними и полностью вымышленными полями; lab не имеет Telegram token и ничего им не отправляет. Итоговый lab export восстанавливается в ещё пустую functional, затем сверяется. Так нужны ровно две D1, без перезаписи занятой финансовой базы. Дополнительные exploratory datasets требуют отдельного согласования, не скрытого reset.

Фиктивную пыль выдавать через согласованную fixture/штатные ledger-инварианты. Например, при известном списке новых test IDs создать отдельную **синтетическую2.0** с балансами100 до0021 и выполнить всю цепочку: opening ledger будет законным. В functional импортировать такой пакет только в пустую базу. Не делать произвольный `UPDATE balance`; не выдавать чужим реальным пользователям настоящие активы.

Если они недоступны, следующий нагрузочный этап не запускать.133 statements не равны133 Worker invocations; internal/schema scans и триггеры могут читать больше ожидаемого.
