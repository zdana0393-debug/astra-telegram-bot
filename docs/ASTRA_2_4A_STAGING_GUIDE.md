## 2. Четыре SQL-шага D1 Console

Dashboard → Storage & databases → D1 → **astra-staging-21** → Console. Проверьте имя ещё раз. Копируйте чистый SQL из следующих файлов и выполняйте **в указанном порядке**:

1. `migrations/0024_steps/01_activity.sql` — новая пустая таблица активных дат, без backfill.
2. `02_history_index.sql` — индекс уже существующего ledger для листания. На большой истории его создание читает/индексирует существующие строки: заранее оценить размер/квоты и время паузы.
3. `03_activity_guard.sql` — защита от чужих/несуществующих профилей и профилей без знака, включая FK OFF.
4. `04_activity_erase.sql` — дополнительный cleanup при удалении профиля, включая старый Worker 2.3B.

Каждый trigger копировать целиком от CREATE TRIGGER до END; не делить по внутренним `;`. При «No SQL statements detected» проверить отсутствие Markdown и полноту оператора. Общий `migrations/0024_activity_history.sql` — точная конкатенация тех же шагов; его используют вместо отдельных файлов, **не в дополнение** к ним. Все CREATE IF NOT EXISTS повторяемы, но это не исправляет чужую/неправильную схему с теми же именами.

## 4. Проверка с телефона и платформенные измерения

- Своим тестовым профилем открыть «✨ Звёздная пыль» → «История операций». До 12 строк на странице, точные суммы/причины, время Europe/Moscow. Opening означает исторический баланс, registration — отдельную регистрацию.
- Пролистать старые страницы, вернуться «Новее». Получить штатный бонус и проверить: старый просмотр не сдвигается, новая строка появляется после «Обновить историю». Кнопки Назад/Главное меню работают. Не менять SQL вручную ради тестовых транзакций.
- «🗂 Досье» → «Экономическое досье»: один активный день сегодня, несколько кликов не добавляют дат/пыли. Другой профиль видит только собственный журнал/серию. Не изображать испытание 90 дней вручную: оно покрыто локальными fake-date тестами.
- На следующей реальной московской дате новое обращение продолжает серию; пропуск целого календарного дня прерывает её при следующем посещении. До окончания текущего дня вчерашняя серия ещё действительна. Этапы 3/7/30 ничего не начисляют.
- Проверить прежние бесплатный прогноз/число, карту дня, Таро −3 с бесплатным повтором, extended −4 с бесплатным повтором, дневной +1, реферал +5, канал +5 и ранее доступный секрет +5 один раз. Отмена подтверждений бесплатна. Магазин остаётся отключённым.
- /privacy перечисляет активные даты и тип обращения. /delete проверять только на своих тестовых профилях: активные даты, ledger, покупки и связи удаляются, чужие данные/анонимный cache сохраняются. Перерегистрация не возвращает старую серию.
- Повторить три integrity-скрипта. Не публиковать исходные пользовательские строки и Telegram ID.

### CPU, D1, объём — до публичного использования

Workers Free в review 2.3B указан как 10 ms CPU HTTP/Cron; D1 Free — 5M rows_read/day, 100K rows_written/day, 5 GB. Проверить актуальные официальные квоты/тариф владельцу. Локальная диагностика `ASTRA_2_4A_METRICS.json` — Node wall-clock и SQLite statements/changes, **не** CPU Cloudflare и **не** D1 rows_read/rows_written. Даже локальная первая операция активности может занимать больше 10 ms wall-clock из-за Intl; делать из этого платформенный вывод нельзя.

В Dashboard Observability/Logs и Metrics собрать отдельно холодные и тёплые HTTP/Cron, CPU p50/p95/max, 1102/другие ошибки. D1 Metrics — счётчики до/после изолированной серии; где доступно — metadata rows_read/rows_written. `changes()` не заменяет rows_written, число SQL-вызовов не заменяет rows_read. Если Dashboard не даёт детализации — отметить проверку незавершённой и отдельно подготовить staging-диагностику для ревью.

| Сценарий | Cold/warm CPU p50/p95/max | 1102/ошибки | D1 rows_read/rows_written |
|---|---|---|---|
| Первый зарегистрированный заход новой даты | не измерено | не измерено | не измерено |
| Повторные клики в ту же дату | не измерено | не измерено | не измерено |
| Первая/старая/обновлённая страница истории | не измерено | не измерено | не измерено |
| Досье с длинной историей активности | не измерено | не измерено | не измерено |
| Таро/extended и бесплатный повтор | не измерено | не измерено | не измерено |
| Бесплатный Cron до 8 профилей | не измерено | не измерено | не измерено |

Новая таблица хранит по одной строке на активного человека/дату. Guard и PK добавляют стоимость; 20 гонок могут дать несколько попыток INSERT, но ровно одну строку. Составной индекс ledger увеличивает стоимость **всех новых финансовых записей**, хотя сами суммы/триггеры прежние. COUNT активных дат и рекурсивная серия читают историю пользователя, стоимость растёт с числом дат. Автоматической очистки личной активности/платных архивов нет. Объём/квоты измерить перед увеличением аудитории; не объявлять неограниченно бесплатную эксплуатацию.

## 5. Ошибка и откат

При сбое — maintenance только тестового Worker, сохранить безопасную диагностику и состояние БД. Откатить **JS** на сохранённый 2.3B, не откатывать SQL и не удалять новые записи/индекс. Его schemaReady игнорирует добавочные объекты; старая экономика/paid snapshot продолжают работать, erase-trigger активности остаётся. Во время отката новые активные даты не фиксируются; эти пропуски не восстанавливать задним числом.

Ошибка записи активности отдельно от денег логируется без ID/текста и не блокирует выдачу прогнозов/Таро; дата может быть пропущена. Умышленно восстанавливать её из ретраев/рассылок нельзя. Принимая релиз, владелец должен оценить эту границу статистики и при необходимости заказать более строгую отдельную очередь восстановления. Доставка Telegram по-прежнему не exactly-once; сохранение результата и одна оплата не устраняют возможное повторное сообщение.

Production и main эта процедура не затрагивает. Stars, новые ставки, delayed referrals и /paysupport — только отдельная будущая 2.4B после согласования.
