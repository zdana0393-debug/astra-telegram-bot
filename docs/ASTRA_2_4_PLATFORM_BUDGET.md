# Astra 2.4: бюджет Workers Free и протокол staging-замеров

7 ноября 2026, Europe/Moscow. Локальные результаты воспроизводятся `node --experimental-sqlite scripts/audit-release-2.4.mjs`; данные — ASTRA_2_4_RELEASE_METRICS.json. Официальные источники закреплены в OFFICIAL_CONTRACT_AUDIT. **Реальных замеров Cloudflare/D1 не было.**

## Подтверждённые ограничения

| Ресурс Free | Ограничение | Что нельзя подменять этим числом |
|---|---:|---|
| CPU HTTP/Cron | 10ms на invocation | Ожидание Telegram/D1 не является CPU; Node wall-clock не доказывает прохождение |
| D1 вызовы | 50 на invocation | Число SQL statements и rows_read/written — другие показатели |
| D1 размер одной базы | 500MB | 5GB — суммарно для аккаунта, не размер astra-staging-21 |
| D1 суммарный размер аккаунта | 5GB | Не отменяет предел каждой базы |
| LIKE/GLOB pattern | 50bytes | Поэтому полный 64-символьный hash ищется диапазоном, не LIKE |
| D1 Time Travel | 7 дней на Free | Не заменяет проверенный backup и своевременное восстановление |

Учитывать также суточные reads/writes/HTTP квоты и активный тариф. Ранее заданные проектом 5Mreads/100Kwrites в сутки требуют сверки перед внедрением с актуальной pricing-страницей. Если квоты исчерпаны, обычный HTTP200 отдельных запросов до исчерпания ничего не гарантирует.

## Измеренные локально вызовы и оптимизация

Baseline34ebcf5: полностью холодный Cron на 8 разных знаках в 06:00UTC требовал 55D1 вызовов; если один знак уже в кэше —53. Это не «риск когда-нибудь», а воспроизведённое превышение 50. Теперь в обоих сценариях успеха/403 —35D1 вызовов,45SQLstatements,9batches,8Telegram mocked calls. Отдельные тесты физически бросают ошибку на 51-м D1-вызове, а не только считают в конце.

Сохранены 8 адресатов, окноCron, idempotent claims, тексты и delivery states. Устранены повторный SELECT после успешного INSERT кэша (RETURNING с каноническим read при конфликте), два лишних roundtrip schemaReady, повторное settlement без изменения знака и неиспользуемое read-back события. Статусы Cron/cleanup записываются через D1.batch. В batch каждый statement по-прежнему выполняется, записи индексов/триггеров не исчезают; экономится invocation roundtrip, а не обещается уменьшение каждой billable метрики. Финансовые triggers/ставки/версии и миграции 0021–0025 не менялись.

Проверены также 4 старые наградные даты + текущая + согласие на invoice в одном HTTP: не превышает 50. Очистка хранит прежние критерии retention, но за один вызов удаляет не более 10payer groups и 10 отдельных закрытых debt accounts; повторять вручную после dry-run до завершения. Один большой payer group всё ещё может содержать много строк: фактические SQL duration/rows_* проверить отдельно.

Таблица — синтетическая выборка, не исчерпывающая гарантия каждого возможного запроса. Сбой/конфликт, длинная история, schema changes и реальные limits могут изменить стоимость. Число Telegram fetch и redirect/subrequest budgets проверить отдельно; CPU может превысить 10ms даже при 35D1calls.

## Диагностика без пользовательских данных

Добавлена обычная text variable `ASTRA_D1_DIAGNOSTICS=true`, **по умолчанию выключена**. Включать владельцу только для согласованного staging-замера. Она не включает награды/магазин, не вызывает дополнительный SQL и не меняет запросы. В конце HTTP/Cron выводится одна JSON-строка:

- d1_calls: реальные вызовы first/all/run/raw/batch; каждый batch считается одним.
- statements,batches,failed_calls: сколько statements,пакетов и отказов наблюдал wrapper.
- rows_read_observed/rows_written_observed,meta_results: сумма доступной D1meta из all/run/batch.
- results_without_meta и rows_complete: first не возвращает meta; **partial-сумму нельзя выдавать за все reads/writes**. Неизвестное не равно нулю.
- db_size_after_max: максимальный meta.size_after в invocation, либо null, если метаданных нет.
- wall_ms: время ожидания+работы, **не CPU**.

Нет SQL,bind-значений,request body,URL с секретами,Telegram ID,charge ID,имён или текста ответа. Счётчики изолированы между параллельными invocation; нет глобального кэша пользовательских данных. При аварийном завершении/1102 строка finally может не успеть попасть в logs — ошибки смотреть также в платформенной аналитике. Retention/доступ Cloudflare logs управляет владелец; не публиковать необезличенные логи.

## Протокол будущих реальных измерений

Это подготовленная инструкция, **не выполняем сейчас**.

1. Пройти checklist установки и backup/restore в отдельной копии. astra-staging-21, общийJS2.4, оба flagsOFF; не менять webhook/production. Зафиксировать deployment SHA/тариф/schema/пустые claims и payments, время окна теста Europe/Moscow и UTC.
2. Создать только собственные синтетические тестовые профили. Обычный staging не выставляет invoices. Для Stars — отдельное будущее разрешение и dedicated Telegram test environment со своей базой.
3. В Dashboard включить Observability/logging и diagnostic flag на согласованное окно. Отделить диагностические вызовы от idle/background traffic; сравнить серию с выключенной диагностикой для оценки её overhead.
4. Для каждого сценария собрать наблюдаемые cold starts и минимум 100warm вызовов, если квоты позволяют. Cold не имитировать фальшивой датой: использовать фактические признаки запуска/первые вызовы после согласованной установки или простоя. Если удалось получить мало cold-проб — указать реальное число, не дополнять выдуманными.
5. CPU p50/p95/max взять из Workers invocation logs/metrics, вместе с wall time и outcomes exceededCpu/1102. Протокол задержки pre_checkout считать от получения HTTP до завершения answerPreCheckoutQuery: schema-проверка включена в 6sbudget,API2,5s. Реальная очередь/сеть может не вписаться; при любом пропуске 10s Stars не принимать.
6. Число D1calls брать из diagnostic counter и сверить с платформенными данными. Общее rows_read/written брать из D1 Analytics/metadata на изолированном окне, вычитая измеренный фон. Нельзя объявлять частичные meta-суммы all/run полным счётчиком при first_without_meta. Если Dashboard не даёт достаточной детализации — проверка остаётся незавершённой, а не «0rows».
7. Зафиксировать DBsize до/после из D1 Dashboard или реального meta.size_after, отдельно index creation/большую историю/paid snapshots. Проверить прогноз роста и запас ниже 500MB; не ждать полного заполнения. Локальная оценка ниже не заменяет этот замер.
8. На выделенной тестовой среде дополнительно проверить реальные 20 конкурентных запросов,5 платежей на одну reconciliation page,ошибкиAPI/D1,refund/debt и чистку одного большого payer group. Не генерировать искусственные транзакции на настоящих профилях ради нагрузки.
9. Выключить диагностику после сохранения обезличенных агрегатов; новые бонусы/магазин не оставлять включёнными по результату одной серии. При превышении 50/10ms/500MB — остановить приёмку, уменьшить работу/согласовать тариф и повторить нужную проверку.

## Хранение: локальная оценка, не ёмкость D1

Скрипт создал 10 профилей×365 активных дат, затем 120 общих cache rows и 100paid snapshots. SQLitepage рост с индексами: около 358KB/профиль/год на наградную активность;8,77KB/общую cache row;5,82KB/owned snapshot с ledger. Точные значения в RELEASE_METRICS.json; округления и выделение страниц малого sample влияют на пропорции.

Ориентиры по этому sample:12 знаков×365 дней общего кэша ≈38,4MB/год;100 активных профилей ≈35,8MB/год только на активность;1000 —≈358MB/год. Если 100 профилей покупают extended ежедневно, ещё≈212MB/год;200 таких профилей вместе с активностью и общим кэшем уже могут превысить 500MB в пределах года. Это не точная дата заполнения: старые данные,UTCtimestamps,payment evidence,рефералы,jobs и свободные страницы добавляют объём.

Планировочный запас: предупреждение при 300MB,блокировать расширение аудитории при 350MB до решения об архивации/тарифе/ёмкости. Это рекомендация для мониторинга, не новый автоматический запрет пользователям. Не удалять paid snapshots/историю или менять /privacy ради вместимости молча. Нужен прогноз с реальным size_after,принятый владельцем.
