# Astra 2.4: архитектура общего релиза A+B

7 ноября 2026, Europe/Moscow. План составлен до реализации; base c08cb9e, подготовленные документы 76c26eb. Только astra-2.4b-rewards-stars. Никакой отдельной установки 2.4A, remote SQL, инвойсов, webhook/production изменений.

## Аудит и основной выбор

0021 немедленно выдаёт referral +5 при выборе знака, CHECK operations разрешает только старые суммы. 0022 начисляет GPT6 +5, 0023 хранит immutable forecast/−4, 0024 добавляет историю/активность. Эти данные/снимки не пересчитываются. Для новых сумм — отдельные версионированные claims и атомарные SQL-триггеры с ledger. Таро −3/extended −4/GPT6 +5 неизменны.

Возвраты — вариант A: min(balance,purchased_dust) снимается один раз, остаток учитывается как refund_debt. Новые положительные ledger-записи автоматически вызывают отдельную отрицательную проводку погашения долга. Старые покупки не меняются. SQL-операции сериализуют гонки refund/purchase/credit, баланс не бывает отрицательным и остаётся равным SUM(ledger).

## Политика и рефералы

D1 singleton — источник состояния policy-v2 и неизменяемой даты старта. Runtime flag ASTRA_ECONOMY_V2_ENABLED по умолчанию false; необязательная ASTRA_ECONOMY_V2_START_DAY обязана совпадать с D1. Администратор может только подготовить будущую московскую дату; активация требует обоих разрешений и наступления даты. activated — необратимый latch. Stop не возвращает старые ставки: новые награды приостанавливаются; расходы/сохранённые материалы продолжают работать. Несогласованные env/D1 не должны тихо менять правила.

Новый профиль после активированного cutover получает отдельный initial claim +12, старые профили — нет. Первый активный день +3, первые три последовательных +3 раз за профиль; +5 на 7/14/21… непрерывной серии; +12 за 30 различных дат после начала политики, включая непоследовательные. Все ключи содержат поколение профиля/версию/тип/дату, не только mutable streak. Существующая activity row на дату не мешает независимому policy-day claim. Сервисные payment/refund/pre_checkout сообщения и Cron не создают активность.

До замены триггера миграция сохраняет legacy-pending и legacy-settled договоры. Старый pending получает исходные +5 при выборе знака даже после cutover; никогда +14 сверху. Для новых v2 договоров две разные подтверждённые активные даты и выбранный знак: +14 пригласившему и +4 приглашённому в одном SQL statement. Удалённый пригласивший отменяет непогашенный новый договор целиком, фантомный баланс не создаётся. Уже проведённые кредиты остаются заработанными, ссылки на удалённый профиль очищаются.

Старые daily/channel callbacks блокируются SQL guards после activated. Старый канал +5 закрывает право на +8. Для writer pause 0025 заменяет astra_referral новым именем: прежний schemaReady больше не готов. Таким образом rollback на 2.4A/2.3B невозможен даже случайно; безопасен maintenance или исправленный совместимый JS. Старые 0021 нельзя повторно применять после 0025 без новой полной проверки.

## Durable interaction

Новый журнал policy events фиксирует update ID, владельца, принятую московскую дату и тип осмысленного взаимодействия до выдачи материала. До миграции существующие jobs помечаются legacy один раз, без ретронаград. Повторы используют исходную дату; журнал не очищается старым 14-дневным Cron. Первичный выбор знака завершается после сохранения даже при Telegram error. Для новой политики сбой долговечной фиксации — retriable error, а не тихая потеря выплаты. В выключенном режиме сохраняется отказоустойчивая статистика 2.4A без новых денег. Дата события фиксируется сервером до бизнес-обработчика, не принимается из клиентского callback.

## Stars

Магазин default OFF. Пакеты snapshot: 10/100, 25/270, 50/570 (XTR/пыль), pack-v1. Один пользовательский подтверждающий экран привязан к Terms version и message ID; payload непредсказуемый, <=128 bytes. Invoice delivery имеет SQL lease: неопределённый исход не вызывает автоматическую повторную отправку. Precheckout проверяет owner/currency/amount/payload/state и резервирует один query ID; бюджет ответа менее 10 секунд. Ни click, ни invoice, ни precheckout не начисляют пыль.

Полученный successful_payment проверяется независимо от текущего shop flag. Уникальные charge ID/hash/order + атомарный receipt-trigger проводят proof/credit/ledger ровно один раз. Сбой квитанции не повторяет кредит. Несопоставимые платежи сохраняются needs_review, а не исчезают. Платёж после удаления профиля не создаёт пользователя: остаётся в suspense и разрешается поддержкой/возвратом.

Окружение проверяется отдельно от shop flag: dedicated Telegram test endpoint /test/, ожидаемый bot ID через getMe, явный owner acknowledgement, отдельная база/scope, согласованные support/Terms/retention. Production требует отдельного явного разрешения реальных Stars. Одного имени staging или boolean недостаточно. Все проверки тестируются только mocks; никакие счета не отправляются в этой задаче.

## Refund/reconciliation/privacy

Администратор с Authorization header создаёт durable refund request; SQL lease даёт один API вызов. После refundStarPayment(true) отдельный immutable external refund notice проводит компенсацию. Timeout/неясный ответ — needs_review, повтор внешнего refund автоматически запрещён. Восстановление — refunded_payment или getStarTransactions. Эти внешние действия и D1 не объявляются одной транзакцией.

Refund, пришедший до successful_payment, подавляет кредит; повторная/конкурентная компенсация защищена PK. Частично потраченный пакет создаёт долг, положительные кредиты погашают его атомарно отдельным ledger delta. Полное удаление/повторная регистрация не стирает долг незаметно. Неоплаченные заказы удаляются с профилем; оплаченные доказательства/ID плательщика и долги сохраняются открыто для поддержки. Срок конфигурируемый и требует отдельного принятия владельцем: кандидат 365 дней после разрешения платежа/долга. Неразрешённые события не удаляются по таймеру. Необратимые charge-hash tombstones остаются для предотвращения повторного кредита после удаления персональных доказательств; это описывается в Terms/privacy, не скрытая антифрод-база.

Пока support/Terms/retention и окружение не согласованы, магазин не запускается. Любой непроверенный аспект реальных Telegram/D1 refund/reconciliation — release blocker коммерческого запуска. Код/симуляция не являются разрешением монетизации.

## Реализованные границы и стоимость

0025 содержит 17 таблиц, 3 индекса и 31 триггер (51 CREATE-объект, включая заменяемые register/operation_guard). Manifest общего Worker требует 77 имён с предыдущей схемой; старое имя astra_referral должно отсутствовать. Девять Console-файлов побайтно составляют объединённую 0025. Снимок прежних jobs выполняется только при migration_done=0. Повтор миграции не начисляет деньги и не превращает новые профили в legacy; это проверено, но на работающей базе миграции не используют как процедуру сброса.

На активной политике capture хранит событие до первого policy_day на дату; повторные действия того же дня не раздувают журнал. Уже известный старый update job не становится новой наградной датой. При неудачной обработке capture остаётся, исходная московская дата неизменна. Settlement обрабатывает до пяти разных дат за попытку, в хронологическом порядке; при остатке возвращает retriable ошибку до бизнес-обработчика. Новые и старые даты не восстанавливаются из Cron. A-activity может сохраниться до финансового сбоя, но отдельный уникальный policy_day/claim корректно допроводится при retry. Утрата старого job после штатного 14-дневного TTL не превращает Telegram update ID в вечную аутентификацию: сохранённые первые policy events устойчивы, общее старое dedup-окно остальных действий остаётся прежним.

Если policy stop пересекает принятую дату, latch всё равно запрещает возврат старых ставок. Профиль нового периода создаётся с 0, обещанный initial12 отложен до resume. Старый профиль никогда не получает этот initial. Поколение профиля фиксируется до opening ledger. **Ключ погашения долга включает generation и исходный ledger key**: повторная регистрация может снова иметь opening:<id>/GPT6 ключ, но не конфликтует с сохранённым погашением прошлого профиля. Платёжная история/долг переживают /delete, наградные права профиля — нет (явный риск злоупотребления в симуляции).

Reconciliation запрашивает максимум 5 транзакций на HTTP, обрезает даже избыточный ответ и возвращает next_offset. Полного автоматического сканирования/Cron-задачи нет; оператор последовательно сверяет перекрывающиеся страницы. Положительное целое XTR, type=user/invoice_payment, source/receiver и scope проверяются; дробные/неподдерживаемые суммы сохраняются для разбора. Бюджет pre_checkout — проверка 6s + API2.5s, без повторного invoice/credit. Отдельное подтверждение актуальности полей и 10s на реальной тестовой среде обязательно.

Хранение: оплаченные orders/receipts, ID плательщика, charge и долговые доказательства открыто сохраняются до закрытия всех дел и истечения принятого срока. Purge работает группой плательщика только после всех разрешённых и достаточно старых заказов, без долга/свежего погашения/открытого дела. Удаление всей группы — одна SQL-команда с cleanup-триггерами; после последнего заказа согласованно удаляются нулевой закрытый account/repayments. Остаточные архивные счета без заказов очищаются отдельной разрешённой процедурой. Постоянный tombstone содержит hash, scope, XTR, размер пакета, реально выданную пыль и признак возврата, без payer. Поэтому поздний подтверждённый refund после purge всё ещё может снять выданную пыль/создать долг. Безличный audit сохраняет тип/дату/hash, не ID человека. Законность и бессрочность этого минимума должен утвердить владелец.

Экономические FAQ/trust, правила удаления, пыль/досье/бонус/рефералы/канал переключают тексты по фактической политике; редакционные/астрологические материалы, авторский FAQ, callback_data старых услуг и генератор не редактируются. Добавлены только новые stars:* callback и команды. Подписка/Таро/extended/GPT6 прежних версий проверены повторно на общем Worker с OFF flags.

Локальные запросы до финального release-hardening: новая наградная дата 28 statements, повторный вход 23, pre_checkout3, credit6, refund5 в синтетическом сценарии; конкретные timings и размер — METRICS.json. Число run statements не включает внутренние записи триггеров/индексов и не равно billable D1 rows_written. На первой дате типично добавляются event/day/activity/claim/ledger плюс jobs; на 3/7/30 и реферальном дне больше claims/ledger. Для 90 непрерывных дат нового профиля без трат: 105 reward claims и соответствующие 105 ledger-строк, плюс регистрационный ledger0 (opening/registration) и отдельные служебные записи. В fixtures явные HTTP полностью подменены. Реальные CPU/1102/rows_* пока не измерены.


## Финальный release-hardening PR #6

Ставки и миграции 0021–0025 сохранены. Общий Worker объединяет schemaReady в один read и устраняет лишнее чтение после cache INSERT через RETURNING; при конфликте остаётся canonical read. Генератор,версии и immutable snapshots не меняются. Рассылка восьми получателям и cleanup используют D1.batch. Финансовые операции сохраняют прежние SQL guards. Полностью холодный Cron55→35D1calls,активный повтор 23→15; актуальные сценарии — RELEASE_METRICS.

После проверки webhook header pre_checkout использует бюджет 6s от входа HTTP,включающий schemaReady и заказ,затем API2,5s. При задержке/частичной схеме следует отрицательный ответ; поздно завершившаяся schema validation не резервирует invoice. Для остальных payment/refund proofs отказ схемы по-прежнему retriable503.

Сверка сохраняет fraction-only invoice-транзакции для разбора; source/receiver используют положительную magnitude amount по официальному сериализатору. Отрицательные исходящие суммы не превращаются в компенсацию. Непустой invoice start_parameter ограничивает forwarding,а owner-check защищает старые счета. Purge ограничен 10+10 группами,поиск 64hex использует диапазон вместо LIKE.

ASTRA_D1_DIAGNOSTICS — необязательные счётчики вызовов/метаданных в отдельном invocation env,без личных ID/SQL/параметров и без дополнительных запросов. Неполная meta у first явно отмечена. Формат и платформенные условия приёмки — PLATFORM_BUDGET. Добавлены src/runtime/diagnostics.mjs и отдельный аварийный maintenance503. Платёжная сверка в Cron,новое антифрод-хранение и реальная активация не добавлены.
