# Astra 2.4: финальный release-hardening

7 ноября 2026, Europe/Moscow. Ветка **astra-2.4b-rewards-stars**, база **astra-2.4-economy**, исходный кандидат **34ebcf5**. Код подготовлен для контролируемой тестовой установки единой 2.4 с **ASTRA_ECONOMY_V2_ENABLED=false и STARS_SHOP_ENABLED=false**, после решения владельца и реальной проверки backup/restore. Это не обещание production-ready и не разрешение включить Stars или новую экономику.

Полный текст review PR #6 из этой среды получить не удалось: GitHub API вернул Forbidden, а анонимная страница PR — 404. Пользователь уведомлён и копию не предоставил. Работа выполнена по семи явным пунктам его запроса; недоступному review не приписываются вымышленные замечания. До принятия PR владелец должен сверить дополнительные пункты по доступному ему тексту.

## Исправления в коде

1. **Реальное превышение лимита D1.** Холодная рассылка восьми разных знаков требовала 55 D1-вызовов; при одном прогретом знаке — 53. Теперь 35: schemaReady объединён в один запрос, cache INSERT возвращает созданную строку через RETURNING, а статусы Cron и очистка используют D1.batch. При конфликте cache INSERT читается каноническая сохранённая запись. Восемь адресатов, окно рассылки, тексты, версии и delivery states сохранены. Проверки успеха, 403, network и malformed реально бросают ошибку на 51-м вызове.
2. **Лишняя работа с наградами.** Убраны повторное settlement после действия без изменения знака, неиспользуемый read-back capture и проверка старой статистической доставки при уже активном наградном трекере. Суммы, дата, backlog, первоначальный выбор знака и восстановление после ошибки сохраняются.
3. **Полный срок pre_checkout.** Шесть секунд теперь включают schemaReady и валидацию заказа от входа HTTP, затем до 2,5 секунды на answerPreCheckoutQuery. Медленная схема вызывает отказ; завершившаяся после отказа проверка не резервирует invoice. Это исправляет прежний отсчёт только после schemaReady. Реальная задержка сети/платформы всё ещё требует проверки.
4. **Платёжные границы.** Invoice получает непустой start_parameter=stars; старые пересланные счета остаются защищены owner-check. В сверке amount — положительная величина с source/receiver по официальному сериализатору. Отрицательные и дробные суммы не округляются; amount=0 с nanostar тоже сохраняется для разбора.
5. **Административные запросы.** Поиск полного 64-символьного hash переведён с LIKE на индексируемый диапазон: D1 ограничивает LIKE/GLOB pattern 50 bytes. Retention purge ограничен 10 группами плательщиков и 10 отдельными закрытыми accounts на HTTP; условия хранения не меняются, страницы выполняются до завершения.
6. **Измеримость и остановка.** Добавлены необязательные invocation counters без SQL, параметров, Telegram ID, charge ID и секретов, по умолчанию OFF. Учитываются D1 calls/statements/batches и доступные meta; неполнота first отмечается явно. Подготовлен отдельный maintenance Worker: только 503/Retry-After, без D1/Bot API и без подтверждения успешного webhook.

## Повторная регистрация и экономика

Аудит усилил прежнюю оценку риска. Новый профиль с первым днём получает 15 ✨, с GPT6 и подтверждённым каналом — 28, то есть до девяти Таро за профиль. При двух активных датах и реферальном договоре приглашённый получает 35, пригласивший 14. Два настоящих локальных цикла удаления/регистрации подтвердили 22 новых Таро и 28 наград пригласившему. Даже в OFF остаётся наследуемая прежняя экономика: 2+1+5+5=13, до четырёх Таро за профиль. Выключение новых флагов не является устранением старого farming.

Предложены три прозрачных подхода: уменьшить ликвидные пробные награды без хранения ID; отдельно согласовать минимальное HMAC-право с TTL 30 дней; ограничить выпуск/допуск пилота без постоянной базы людей. У каждого есть границы, включая мультиаккаунтность и новый цикл после TTL. Ничего из этого не внедрено молча. Точные последствия, будущие тексты /privacy и требования к очистке — **ASTRA_2_4_REGISTRATION_ABUSE.md**.

**ASTRA_2_4_ECONOMY_OPTIONS.md/JSON** сравнивает текущий, сбалансированный и экономный варианты:

| Вариант | 7 дат | 30 дат | 90 дат | 365 дат |
|---|---:|---:|---:|---:|
| Текущий кандидат | 41 | 137 | 357 | 1382 |
| Сбалансированный | 19 | 57 | 141 | 536 |
| Экономный | 11 | 40 | 108 | 423 |

Это начисленная пыль новому профилю без расходов/дополнительных бонусов. Отдельные таблицы показывают расход на Таро, extended, смешанную стратегию, пропуски, роль пакетов Stars и выпуск на 1000 профилей. Основной прогноз с числом дня и карта дня бесплатны во всех вариантах. Таро стоит 3, extended 4, GPT6 даёт 5; эти контракты сохранены. Альтернативы существуют только в планировочном скрипте. Текущий кандидат 12/3/3/5/12/14+4/8 остаётся в runtime, но не активирован.

Прямые сайты Telegram/Cloudflare недоступны (CONNECT 403). Проверены официальные публичные исходники Telegram Bot API и Cloudflare Docs на закреплённых коммитах; ссылки и SHA файлов — **OFFICIAL_CONTRACT_AUDIT / OFFICIAL_SOURCES**. Платёжные service-поля вложены в **message**, не являются самостоятельными allowed_updates. Существующий список/webhook не изменён.

Исходники не доказывают работающий endpoint, актуальные коммерческие правила и прохождение срока 10 секунд. Для Stars остаются внешняя проверка документации и dedicated Telegram test environment. Обычный staging-бот способен выставить настоящий XTR-счёт.

Подтверждены Free-лимиты: **10 ms CPU HTTP/Cron, 50 D1-вызовов на invocation, 500 MB на одну базу, 5 GB на аккаунт**. Исправлена неоднозначность прежних инструкций. Разработан протокол staging CPU/D1 calls/rows_read/rows_written/size, включая холодный Cron, большие истории, платёжные ошибки и storage growth. Локальная SQLite-оценка показывает, что активность и платные snapshots способны заполнить 500 MB даже без большой аудитории; её нельзя принимать за точный capacity forecast. Реальные метрики остаются незаполненными в PLATFORM_BUDGET.

Команда **sh scripts/test-2.4.sh**, Node **24.22.1**: **511 node:test + 210 legacy assertions**, 0 failed/cancelled/skipped. Сохранён весь предыдущий pipeline; добавлены **24 release-hardening проверки**. Все финансовые HTTP-вызовы подменены; локальный SQLite, синтетические профили и даты.

- Наследуемые функции повторно проверены на общем Worker; старые оплаченные Таро/прогноз из реального локального 2.4A сохранились после 0025 и чтения общим Worker/OFF без изменения денег/текстов.
- Год фактических вызовов Worker совпал с текущей моделью 7/30/90/365; модели сохраняют сумму пыли при альтернативных стратегиях расхода.
- Успешный платёж при полном отказе D1 возвращает 503 и затем проводится один раз. Поздний webhook после cleanup jobs и новой регистрации не повторяет кредит.

Ранее проверенные 180 независимых SQLite connections, fault injection, долги/ретраи, FK ON/OFF, partial schema, 14 integrity-групп, прогнозы/число/Таро и весь редакционный аудит снова включены. Сборка и syntax/whitespace проверки пройдены. Прямые экраны теперь включают фактическую страницу с проводкой погашения, а не только первую страницу при равных timestamp.
