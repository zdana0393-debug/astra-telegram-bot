# Задание для Codex — ASTRA 2.2: облик, навигация и легенда
**Основа:** `astra-2.2-shell`, создана от полностью проверенного кандидата `astra-2.1-hardening`.
**Режим:** разработка исключительно для отдельного staging Worker и D1. Продакшен Astra 2.0 не изменять.
**Язык интерфейса и отчётов:** русский.

1. `docs/ASTRA_3_0_SPEC_v0_2.md` — разделы 1, 2, 3, 12, 13, 16, 17, 18 и примечания v0.2. Это главный источник продуктовых решений.
2. `docs/AstraBot_MASTER_v1.0.md` — справочник символических значений, не подменять его случайными выдумками.

4. `migrations/0021_wallet.sql`, `scripts/check_integrity.sql`, `tests/hardening.test.mjs`, `docs/ASTRA_2_1_AUDIT.md`, `docs/ASTRA_2_1_MIGRATION.md` — понять технические инварианты 2.1.
5. `AGENTS.md`, `README.md`. Если они формулируют ограничения только для 2.1, сохранять общую безопасность и применять более новое задание именно к новой ветке 2.2.

## 1. Главная цель
Сделать **ASTRA 2.2 — цельную, эстетичную текстовую оболочку** для Telegram-бота:
- Космическое бюро символической навигации: торжественный, интеллигентный, хладнокровный тон; чуть-чуть скрытого абсурдного «небесного делопроизводства».
- Никаких дешёвых мемов, откровенных шуток или карикатуры на любителей астрологии; никаких страшилок.
- Визуальная система на этом этапе только **текст, Unicode-символы, кнопки, разделители, короткие вступления**; никаких сгенерированных картинок и платных API.
- Не употреблять пользовательское слово «оккультный».
- Фактические заявления строго отличать от символических и от художественных легенд. Не выдавать вымышленных специалистов за реально сертифицированных учёных.

## 2. Компактная главная клавиатура — шесть пунктов, два в ряд
Рекомендуемые названия из спецификации, при необходимости небольшая редактура:
1. «🌙 Прогноз дня»
2. «🃏 Таро»
3. «🪞 Познай себя»
4. «🗂 Досье»
5. «✨ Звёздная пыль»
6. «🏛 Об Астре»

Переходы 2–3 шага максимум; понятная кнопка «Назад» и «Главное меню» в подменю. Разрешено сочетать reply и inline keyboard, но не ломать callback_data старых открытых сообщений. Обрабатывать некорректные и просроченные callbacks спокойно.

**Не удалять существующие рабочие функции**: выбор 12 знаков; бесплатный прогноз с **числом дня**; бесплатная карта дня; оплачиваемый трёхкарточный расклад по 3 ✨; начальные 2 ✨; +1 ✨/сутки; +5 рефереру; +5 за подтверждённый канал; баланс; пригласить друга; настройка рассылки; `/start`, `/stop`, `/help`, `/privacy`, `/delete`; Cron. Перенести функции внутрь новых подменю. Не изменять стоимость и логику цен в 2.2; полноценный расширенный гороскоп и изменение экономики — в будущих версиях.

Для «Познай себя», продвинутой натальной карты, совместимости, архива коллекций, магазина Stars показывать **красивое, честное «в подготовке»**, без кнопок, которые списывают деньги или обещают несуществующие услуги. Можно показывать описание планируемого раздела. Единый «Досье» пока показывает честные сохранённые данные (знак, баланс, включена ли рассылка), без выдуманной статистики. Если технически не нужен новый сбор персональных данных — не вводить его.

## 3. «Об Астре» — полноценная театральная справка
Вложенные разделы:
- «Что такое Астра» — короткий манифест Космического бюро и его миссия;
- «Почему Астре доверяют» — **объяснение внутренних правил и прозрачности**, а не рекламные обещания: отдельные тексты для существующих гороскопов, карт Таро и звёздной пыли. Будущие сервисы пометить «разработка продолжается». Не обещать реальные астрономические расчёты, если их ещё нет.
- «Команда» — художественные роли, имена и акростих из спецификации: Gideon Vale, Percival North, Thalia Wren, 6th Registry. Первые символы строк читаются вертикально как `GPT6`. Добавить M. Ejaculatum как малозаметную фигуру легенды, без похабного юмора в видимом тексте. Не выделять секретную фразу отдельной подсказкой и не объяснять пасхалку в обычном интерфейсе.
- «FAQ» — содержательные, компактные ответы с возможностью открыть более подробный ответ: чем является гороскоп, как формируются ответы, почему колоду «хранит один хранитель» (это традиция **легенды**, а не универсальный исторический факт), почему нет гарантий, что такое пыль, можно ли бесплатно пользоваться, как используются данные, какие функции ещё не созданы.
- «Правила и приватность» — прозрачная ссылка/раздел на реальные `/privacy`, `/delete`; не утверждать о конфиденциальности того, что на деле сохраняется.

Поддерживать красивую стилистику, но сохранять читабельность на телефоне (никаких огромных полотен в одном сообщении; соблюдать лимиты Telegram).

## 4. Пасхалка GPT6
Пользователь вводит `gpt6` в личный чат (регистр неважен, пробелы по краям игнорируются), получает **однократный** стилизованный ответ «архив открыл дело» и **+5 ✨**, как указано в спецификации. Повторный ввод не выдаёт награду повторно; возможен короткий архивный ответ без начисления.
- **Никаких прямых `UPDATE balance` из JS** без ledger. Сохранить инвариант 2.1: сумма `astra_wallet_ledger.delta` равна `astra_users.balance`.
- `astra_operations` имеет SQLite `CHECK`, допускающий только `daily/channel/referral/tarot`; **не вставлять фиктивную награду как referral или channel** и не обходить CHECK. Сделать отдельную **аддитивную миграцию** `migrations/0022_shell.sql` с небольшой таблицей one-off наград и атомарным триггером, который в одном SQL statement обновляет balance и добавляет запись ledger с уникальным idempotency_key, `operation_id=NULL`, и понятным `reason='easter:gpt6'`; либо предложить равнозначный чистый вариант, сохраняющий неизменённый CHECK. Согласованность/rollback тестировать.
- Награда за код должна быть ограничена уникальным ключом по пользователю и коду даже при конкурентных разных update_id.
- Удаление профиля через `/delete` обязано очищать запись пасхалки **даже в SQLite-сценарии с foreign_keys=OFF** (при необходимости аккуратно заменить `astra_erase` миграцией, без потери остальной логики). После `/delete`/повторного `/start` данные удалённого пользователя считаются новым профилем, как в 2.1.
- При отсутствии миграции 2.2 должно быть **явное безопасное 503/health not ready**, а не частично работающий интерфейс со сломанной пасхалкой.
- Миграция D1 должна запускаться **только на staging, вручную после ревью**. Файл разбить на небольшие части в `migrations/0022_steps/`, если это нужно для Cloudflare SQL Console (ранее длинный SQL с несколькими триггерами выдавал «No SQL statements detected»). **Не запускать remote SQL самостоятельно**.

## 5. Качество интерфейса и совместимость
- Сообщения сохраняют профессиональную «небесно-канцелярскую» эстетику, при этом дают понятную практическую информацию. Сдержанный юмор на втором плане.
- Новый тариф, рекламная подписка, Stars, картинки, полноценная натальная карта, 78-карточное Таро, анкеты — **вне этого релиза**.
- Число дня должно остаться в бесплатном прогнозе; сохранение расчёта и текстов базового гороскопа v2.1 до отдельного релиза 2.3.
- Сохранить и проверить расчёт Moscow day; не менять бонусы, стоимость Таро, DB binding `DB`, защиту webhook и тариф Free.
- Проблема тестового username: в 2.1 есть жёстко заданный `BOT_USERNAME='LaDa_Iskra_Opel_Astrabot'`, а на staging это вручную менялось на имя тестового бота. В 2.2 сделать **настраиваемый `env.BOT_USERNAME`** (только безопасный username без @, fallback к исходному продакшен-username); инструкции для тестового Worker явно предписывают задать обычную text variable `BOT_USERNAME` равную фактическому username тестового бота. Не просить и не записывать секреты.
- Важно: код 2.2 должен исходить из **актуального release 2.1**, а не переписывать весь бот с нуля.
- Максимально возможная удобная навигация в Telegram, но `editMessageText` применять только если это не ломает retries и не создаёт повторных списаний.
- Не менять активный production webhook, продакшен-Worker, Cron и D1 `astra-live-v2`. Не импортировать реальную базу для локальных тестов.
