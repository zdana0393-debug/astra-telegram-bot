## Почему владелец подтверждается отдельно

Локально набранный ID не доказывает владение аккаунтом. Подготовка не запрашивает ID и не выдаёт права. Закрытый bootstrap использует действующий проверенный webhook, существующие секреты и приватный случайный challenge на 15 минут после применения SQL. Только личное `/owner_claim …` от живого зарегистрированного аккаунта без пересылки даёт подписанное HMAC подтверждение. В приватном ответе бот связывает ID/поколение профиля, bot_id, номера сообщения/update, challenge и SHA новой сборки. Секрет не передаётся.

`ASTRA25_1_CONFIRM.py` проверяет подпись **локально** существующим HMAC-ключом и сохраняет приватные proof/attested receipt. Вручную введённый ID не принимается. Затем `ASTRA25_1_STAGE.py` может подготовить owner-bound конфигурацию. До этого `/admin` и `/grant` закрыты; неутверждённый/чужой `ASTRA_OWNER_TELEGRAM_ID` даёт readiness503.

Важная последовательность: сообщение владельца должно действительно обработать новое закрытое bootstrap-ядро. Неактивная версия с 0% трафика сама не получает webhook. Поэтому подтверждение НЕ считается выполненным до отдельного разрешённого контролируемого включения bootstrap. После подтверждения потребуется ещё версия конфигурации с тем же кодом и attested ID. Ни один из этих шагов Codex не выполнял.

## Исправление доставки pre-checkout без раскрытия секрета

После активации владелец подтвердил настоящие `ready/admin_ready/stars_ready=true`, пустые blockers и100% трафика на новой версии. При первой попытке оплаты Telegram сообщил об истечении запроса. Безопасный локальный `getMe/getWebhookInfo` владельца подтвердил основной адрес, отсутствие ошибок доставки и **allowed_updates=[message,callback_query]**, без `pre_checkout_query`. Значит платёжный запрос Telegram не передавался в Worker. Зелёный `/health` проверял operational configuration, не внешний список Telegram. BotFather/provider для XTR не требуется.

Telegram не возвращает значение webhook secret. В официальном сохранённом Client.cpp (process_set_webhook_query/finish_set_webhook) отсутствие `secret_token` при повторной установке очищает его. Поэтому небезопасно вызывать setWebhook только с URL и новым списком. Новый отдельный патч использует **существующий runtime secret внутри Worker**, без копирования его в Windows/чат.

- `src/astra251/webhook-repair.mjs`: только аутентифицированный свежий личный message подтверждённого владельца. `/stars_webhook_check` читает actual getMe/getWebhookInfo; `/stars_webhook_enable` проверяет bot_id, фиксированный прежний URL, сертификат, max_connections, owner/generation/schema и добавляет только pre_checkout_query. Сохраняет все прежние типы, secret_token из env, max_connections; явно drop_pending_updates=false. Не меняет токен, URL, Cron, D1, тарифы или покупки. Неизвестные настройки/несовпадение бота закрывают операцию. Собственный сертификат не поддерживается и отклоняется; IP override не вводится (исходный webhook использует обычный DNS).
- После сетевой неопределённости setWebhook выполняется readback; автоматического повторного setWebhook нет. Повтор команды сначала читает состояние и при уже разрешённой доставке ничего не меняет. Ошибки содержат только фиксированные коды. Никаких публичных repair HTTP routes, getUpdates, invoice/refund API или secret echo.
- `release/ASTRA_2_5_1_WEBHOOK_PATCH.json` — отдельная additive delta поверх **неизменённого** первоначального2.5.1 package. Три точные замены: дополнительный закрытый модуль, message wrapper и версия `ASTRA-2.5.1-stars-admin-webhook`. Registry literal сохраняется побайтово. SQL/схема323 и исходный пакет не меняются.
- Самостоятельная Windows-программа `ASTRA25_1_FIX_STARS_WEBHOOK.py` генерируется из template. Только локально проверяет оригинальный receipt/base template/hash, приватные права и registry; Node проверяет синтаксис. Создаёт отдельный `ASTRA_2_5_1_WORKER_WEBHOOK.js` и новый private receipt, старые файлы не заменяет. При повторе допускается только идентичный результат. Копирует UTF-8 код в буфер, без сети и чтения Telegram token/webhook secret.
- `ASTRA_ADMIN_BUILD_SHA256` остаётся прежним **якорем первоначального подтверждения владельца**, соответствующим записанному HMAC proof. Менять его, повторять owner_claim или править owner SQL не нужно. SHA нового исполняемого Worker записывается отдельно в `ASTRA251_WEBHOOK_PATCH_RECEIPT_PRIVATE.json` (`worker_sha256`); поле `owner_authority_sha256` явно обозначает прежний authority hash. Это непрерывность прежней роли, а не утверждение, что старый proof подписывает новый код.

Будущее применение владельцем: запустить локальный patcher в прежней приватной build-astra251 папке; новый проверенный код будет в буфере. В существующем Worker заменить только код через Edit code/Deploy, сохраняя bindings/все vars/secrets, и проверить фактическую версию и100% трафика. Затем в личном чате с ботом отправить `/stars_webhook_enable`. После подтверждения **создать новый счёт** через магазин; просроченный счёт не переиспользовать.
