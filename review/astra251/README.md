## Почему владелец подтверждается отдельно

Локально набранный ID не доказывает владение аккаунтом. Подготовка не запрашивает ID и не выдаёт права. Закрытый bootstrap использует действующий проверенный webhook, существующие секреты и приватный случайный challenge на 15 минут после применения SQL. Только личное `/owner_claim …` от живого зарегистрированного аккаунта без пересылки даёт подписанное HMAC подтверждение. В приватном ответе бот связывает ID/поколение профиля, bot_id, номера сообщения/update, challenge и SHA новой сборки. Секрет не передаётся.

`ASTRA25_1_CONFIRM.py` проверяет подпись **локально** существующим HMAC-ключом и сохраняет приватные proof/attested receipt. Вручную введённый ID не принимается. Затем `ASTRA25_1_STAGE.py` может подготовить owner-bound конфигурацию. До этого `/admin` и `/grant` закрыты; неутверждённый/чужой `ASTRA_OWNER_TELEGRAM_ID` даёт readiness503.

Важная последовательность: сообщение владельца должно действительно обработать новое закрытое bootstrap-ядро. Неактивная версия с 0% трафика сама не получает webhook. Поэтому подтверждение НЕ считается выполненным до отдельного разрешённого контролируемого включения bootstrap. После подтверждения потребуется ещё версия конфигурации с тем же кодом и attested ID. Ни один из этих шагов Codex не выполнял.

## Будущая установка — только по отдельному разрешению

1. Согласовать writer freeze: входящие webhook и Cron не должны писать во время изменения схемы. Сохранить **текущие** версию Worker, DB binding, секреты (только имена), Cron, compatibility flags/date, channel, observability, остальные bindings/vars. Не использовать старый локальный TXT как источник текущих runtime-настроек.
2. Получить резервную копию D1 штатным способом, восстановить её в разрешённую изолированную базу и проверить балансы/ledger, купленные тексты и snapshot SHA, платёжные доказательства/долги, рефералов, HMAC и согласия. Реальное восстановление здесь **NOT_TESTED**. До успешного restore — STOP.
3. На копии применить SQL0032 ровно один раз целым проверенным файлом/поддерживаемой D1-операцией. SQL содержит read-only точную проверку старых286 DDL до первого изменения, затем37 добавленных объектов и три точечные замены неподдерживаемого admission-PRAGMA. Сверить все323 DDL через `scripts/check_integrity_astra251.sql` и `/health`. Нулевые `violations` обязательны. Не удалять guard и не менять manifest ради зелёной проверки.
4. Проверить настоящие readonly `meta.size_after`, JSON/MATERIALIZED, триггеры, rollback, конкурентные покупки/начисления и удаление. Измерить cold/warm CPU, startup, D1 calls/rows_read/rows_written, storage/1102. Локальная SQLite и Wrangler dry-run этого не доказывают.
5. Проверенный полный **актуальный** снимок конфигурации нужен локальному STAGE. Его контракт: `{active_version_id,captured_at,reviewed_complete_current_config:true,configuration:<полная текущая Wrangler-конфигурация>}`. Это не шаблон для ручного редактирования: снимок должен быть получен отдельным согласованным read-only чтением Cloudflare. Пока такого снимка нет, автоматическая staging-процедура **BLOCKED**. Скрипт отклоняет ошибочный Worker/DB, секреты в plain vars, неподдерживаемые assets/build hooks, включённые новые функции. Все неизвестные обычные vars и runtime-настройки сохраняются; значения channel/logs не угадываются.
6. STAGE **только формирует приватный план** `versions upload` и конфигурацию. Не выполняет команду, SQL или API. Не содержит `--secrets-file`, не перевыкладывает HMAC и не вращает секреты. Bootstrap и owner mode имеют отдельные immutable файлы, поэтому первый план не мешает второму. Перед будущим выполнением сверить текущую версию ещё раз; использовать только `versions upload`, без `versions deploy`, `deploy` или `triggers deploy`. Загрузка0% тоже требует разрешения. Сохранить **реальный** Version ID из успешного ответа; при неизвестном исходе сначала проверить список версий, без слепого повтора. Preview URL не предполагается.

Применить приватный `OWNER_CHALLENGE_PRIVATE.sql` в согласованном окне, затем владелец отправляет содержимое `OWNER_CLAIM_PRIVATE.txt` только своему существующему боту. Никому не пересылайте challenge/proof.
8. Запустить `ASTRA25_1_CONFIRM.py`, выбрать новую приватную папку и вставить только подписанную строку ответа. Запустить STAGE в owner mode по новому текущему снимку. Проверить отдельно разрешённую конфигурацию и `/health`: ready/admin_ready true, stars_ready false. Обычный и одноразовый `/grant`, себе/другому зарегистрированному профилю, история/долг/повтор webhook проверяются отдельно, без настоящих Stars.

## Если восстановление экспорта сообщает `no such table: main.astra_users`

В PR добавлен локальный `ASTRA25_1_VERIFY_BACKUP.py`. Запустить из распакованного репозитория и выбрать скачанный `ASTRA251_BACKUP_BEFORE_0032.sql` в исходной приватной build-папке. Программа создаёт новую защищённую папку, проверяет порядок и сохраняет каждую исходную DDL/data-команду, создаёт таблицы до INSERT и триггеры после данных. FK остаются ON; проверка переносится до COMMIT, но не отключается. Неизвестные команды отклоняются. Исходный SQL и предыдущая неудачная локальная база не меняются.

Затем выполняются точная проверка286DDL, целостность/FK/ledger/paid, копирование восстановленной базы и настоящая миграция0032 на этой копии, проверка323DDL и всех старых данных/типов/rowid. Результат — только LOCAL PASS; реальный Cloudflare restore и равенство скрытых исходных rowid по одному SQL dump этим не доказываются. Сверить итог с текущей read-only инвентаризацией: на момент последнего ответа владельца1 пользователь/4 пыли. Не импортировать созданные SQLite/SQL в production по собственной инициативе.

Файл предназначен для локальной проверки, не вызывает Wrangler, Cloudflare или Telegram. При ошибке показывает безопасные названия этапа/кода, без сырого SQL и содержимого записей.

Если старая версия VERIFY_BACKUP выдала `LOCAL_RESTORE_INTEGRITY_TAROT29_AUDIT_FAILED`, используйте обновлённый архив PR и снова запустите **тот же VERIFY_BACKUP** с прежним SQL-файлом.
